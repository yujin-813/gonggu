## 한 문장

**꿀공구는 인스타그램 공동구매가 진짜 싼지 판정해주는 서비스다.**

공구를 모아 보여주는 것이 목적이 아니다. 모아 보여주는 건 판정을 붙이기 위한 준비다.

---

## 해결하려는 문제

인플루언서 공구는 "최대 87% 할인" 같은 말을 앞세우지만, 사는 사람은 그게 사실인지 확인할 방법이 없다. 상품마다 판매처를 일일이 찾아 비교해야 하는데 공구는 대개 2~3일 안에 끝난다.

**그렇게 판단한 근거:**
- 실제 데이터에서 자동 수집한 비교가 26건이 명백히 잘못돼 있었고(신일 제습기 399,000원 → 2,900원 매칭 등), 그중에는 40% 할인 상품이 "아쉽딜"로 뒤집힌 사례가 있었다 → `D-006`
- 카드가 판정과 따로 할인율을 계산하던 시기, 공개 247건 중 **33건**이 서로 다른 숫자를 보여줬다. 그중 일부는 실제로 더 비싼 상품을 "20% 저렴"이라고 표시했다 → `D-014`

즉 **가격 비교는 사람이 눈으로 하기 어려울 뿐 아니라, 기계도 틀린다.** 틀린 걸 걸러내는 것이 이 제품의 일이다.

---

## 대상 사용자

**대상:** 인스타에서 공구 링크를 보고 "이거 진짜 싼가?"를 3초 안에 알고 싶은 사람. 대부분 모바일에서 인앱 브라우저로 들어온다.

- 실측: 방문의 63%가 아이폰·아이패드, 24%가 인앱 브라우저(인스타·카톡), 12%가 안드로이드 (2026-08-19 nginx 로그)
- 네이버 검색 유입은 모바일이 PC의 4.6배 (88건 vs 19건)

**대상이 아닌 사람:**
- ⚠️ *이 칸은 사장님이 직접 채워야 합니다.* 코드로는 알 수 없는 판단입니다.
- 코드에서 유추되는 것: 최저가를 끝까지 파는 사람(우리는 대표가 하나만 비교한다), 공구를 여는 인플루언서 본인(공급자용 기능이 없다)

## 중심 원칙

각 원칙마다 **코드 어디에 강제되는지**를 함께 적는다. 강제되는 곳이 없으면 그렇게 표시한다 — 그게 다음에 깨질 규칙이다.

### 1. 화면에 나가는 숫자는 한 곳에서만 나온다

할인율·비교가·판정은 전부 `getDealVerdict()`를 거친다. 컴포넌트가 따로 계산하지 않는다.

- **강제되는 곳:** `lib/dealGrade.ts` — 카드·상세·공유 카드가 모두 이 함수의 반환값만 읽는다. `components/PostCard.tsx`의 `savedChip`도 여기서 파생된다.
- **깨진 적 있음:** 예전에 `PostCard`가 `origPrice`로 직접 계산해 33건이 어긋났다 → `D-014`

### 2. 확신이 없으면 말하지 않는다

비교가가 없으면 등급을 매기지 않는다. 판정할 수 없는 유형(여러 상품 공구)은 판정하지 않는다. 할인율이 0 이하면 카드에 아무 말도 쓰지 않는다.

- **강제되는 곳:** `lib/dealGrade.ts`의 `pending`/`multi` 상태, `PostCard.tsx`의 `savedChip`이 `discountRate <= 0`이면 `null` 반환
- **강제되는 곳:** `lib/optionScrape.ts`의 `looksSoldEnded()` — 판매종료 판정을 좁게 잡는다. 애매하면 "못 읽었다"고 한다

### 3. 자동으로 얻은 값은 사람이 확인한 값보다 못 믿는다

- **강제되는 곳:** `lib/dealGrade.ts` — `verified`(사람이 넣은 `origPrice`·`purchase_links` 가격)와 `auto`(`market_price`)를 나눠 담고, 자동값이 공구가의 50% 미만이면(`AUTO_MATCH_FLOOR`) 기준에서 뺀다
- **강제되는 곳:** 수집기가 자동으로 채운 옵션은 대표가를 바꾸지 못한다 (`inpock.py`, `backfill_options.py`) → `D-011`

### 4. 구매 링크 없는 공구는 공개되지 않는다

"공구 보기"를 눌렀는데 인스타 게시글이 뜨면 신뢰를 잃는다.

- **강제되는 곳:** `lib/postGuards.ts`의 `enforcePurchaseLinkRequirement()` — `ready`/`published`로 저장되려는 순간 `needs_review`로 되돌린다. 관리자 등록·수정·빠른 승인·제보 폼이 모두 `app/api/posts`와 `app/api/posts/[id]`를 거치므로 한 곳에서 커버된다
- 파이썬 수집기는 별도로 `classify_status()`에서 같은 규칙을 적용한다 (⚠️ 두 곳에 있어 갈라질 수 있음 — `03-SYSTEM.md` 알려진 문제 참고)

### 5. 색은 의미가 있을 때만 쓴다

- **강제되는 곳:** `app/globals.css` — 주황은 꿀딜 판정과 CTA에만, 빨강은 오늘·내일 마감에만, 초록은 혜택(할인율)에만. 등급은 꿀딜만 채운 색이고 나머지는 글자색으로만 구분한다
- ⚠️ **CSS 규칙일 뿐 강제 장치는 없다.** 새 컴포넌트에서 임의의 색을 쓰면 막을 방법이 없다. 다음에 깨질 가능성이 가장 높은 원칙이다

## 하지 않기로 한 것

| 하지 않는 것 | 이유 | 재검토 조건 |
|---|---|---|
| 사이트 안에서 결제 | 모든 구매는 외부몰에서 일어난다. 결제를 붙이면 정산·환불·CS가 전부 따라온다 | 거래액이 직접 붙일 만큼 커질 때 |
| 남의 쇼핑몰 장바구니에 담기 | 아임웹 2단계 옵션은 장바구니에 담아야 가격이 나오는데, 남의 상점에 쓰기 동작을 하는 건 선을 넘는다 | 없음 (원칙 문제) |
| 사이트별 크롤러 만들기 | 구매 링크 도메인이 40종 넘게 흩어져 있다. 만들어도 개편 한 번에 깨진다. 대신 솔루션 단위(위즈·카페24·아임웹)로만 대응하고 나머지는 붙여넣기로 받는다 | 한 도메인이 전체의 20%를 넘길 때 |
| 댓글 기능 | 사람이 없으면 빈 댓글창이 오히려 신뢰를 깎는다 | DAU 약 300 |
| 키워드 알림 | 알림 보낼 대상이 없다 (푸시 구독자 2명) | DAU 약 100 |
| 최저가 끝까지 추적 | 대표가 하나로 비교한다. 옵션별 최저가를 다 좇으면 판정이 늦어지고 틀릴 여지가 커진다 | ⚠️ 미정 |
| ⚠️ PM2 cluster 다중 인스턴스 | 서버 메모리 1.9GB(가용 862MB)에서 빌드와 겹치면 OOM 위험이 무중단 이득보다 크다 | 인스턴스 사양 상향 또는 스왑 확보 시 |
