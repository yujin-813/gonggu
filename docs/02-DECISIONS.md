## D-071 · 관리자 목록에 페이지 번호 매김 추가 + 중복 목록에 삭제 버튼 · 2026-08-28

**상태:** 유효

**상황** — D-070에서 만든 「같은 공구로 보이는 중복」 목록에 "열어보기"만 있고 삭제가 없어서
불편하다는 피드백. 겸사겸사 사장님이 관리자 화면 전체가 끝없이 이어지는 스크롤(공구 목록은
최대 2,570여 건이 한 번에 다 그려진다)이 싫다고 해서, 페이지 번호로 자르고 10/50/100개씩
고를 수 있게 해달라고 요청.

**결정**
- 공용 `Pagination` 컴포넌트를 만들어 (1) 「공구 관리」 탭의 전체 공구 목록, (2) 「같은
  공구로 보이는 중복」 목록 두 곳에 적용했다. 처음·이전·페이지 번호·다음·마지막 버튼과
  10/50/100개씩 선택을 같이 둔다. 필터·검색이 바뀌면 1페이지로 돌아간다(안 그러면 이전
  필터의 뒷페이지에 있다가 빈 화면을 보게 된다).
- 중복 목록의 "열어보기" 옆에 "삭제" 버튼을 추가했다 — 이미 있는 `deletePost()`(확인창 +
  DELETE 호출)를 그대로 재사용했다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 무한 스크롤(스크롤하면 자동으로 더 불러오기)로 바꿈 | 사장님이 명시적으로 "무한스크롤 싫어"라고 했다. 페이지 번호가 요청 그대로다 |
| 중복 목록에 "일괄 삭제" 버튼도 추가 | 요청은 "삭제 버튼만 넣어달라"였다. 일괄 삭제는 실수로 다른 상품까지 지울 위험이 커서 요청받지 않은 걸 임의로 늘리지 않았다 |

**받아들인 대가** — 없음.

**당시 확신도** — 높음. tsc·build 클린. 로컬에서 실제 서버 데이터로 두 목록의 페이지 번호·
페이지 크기 전환·중복 목록 삭제 버튼까지 브라우저로 직접 확인함.

## D-070 · 수집기 중복 방지 지문에서 시작일을 뺌 + 관리자에 중복 목록 표시 · 2026-08-28

**상태:** 유효

**상황** — 사장님이 검수 필요 목록에서 이미 공개된 것과 완전히 같은 제목의 글을 발견하고
중복 여부를 확인해달라고 했다. 원인을 추적해보니 `inpock.py`가 "이미 수집했는지" 판단하는
지문(fingerprint)이 제목·가격·**시작일**·마감일을 합쳐 만드는데, 시작일은 "공구 일정" 블록과
상품 링크 블록을 매칭하는 `match_schedules()`가 매번 성공한다는 보장이 없다 — 이번 건도
8/24 수집 땐 매칭에 성공해 시작일이 채워졌는데, 8/28 수집 땐 매칭에 실패해 빈 값이 됐다.
내용은 완전히 같은데 지문만 달라져 새 글로 다시 수집됐다.

전체 데이터에서 규모를 확인하니 같은 블록·같은 제목인데 별도 글로 남아있는 경우가
233그룹(469건), 그중 둘 다 아직 살아있는(공개 중이거나 검수 대기) 경우가 207그룹이었다.

**결정**
- `inpock.py`의 fingerprint에서 시작일을 뺐다(제목+가격+마감일만). 시작일이 바뀌는 것만으로는
  "새 공구"로 보지 않는다. 마감일은 남겼다 — 인플루언서가 직접 쓴 값이라 여전히 의미가
  있고(연장·재오픈을 새 내용으로 잡아야 함), 시작일과 달리 매칭 실패로 생기는 값이 아니다.
- 지금 이미 생겨있는 중복 207건은 자동으로 정리하지 않는다. 관리자 「공구 관리」 탭 맨 위에
  목록만 띄워서(`DuplicateGroups`) 사장님이 직접 확인·판단하게 했다 — 잘못 짝지어 진짜
  다른 상품을 지우는 위험을 피한다. 각 항목에 "열어보기"를 두어 수정 화면으로 바로 갈 수
  있게만 했다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 시작일·마감일 둘 다 지문에서 뺌 | 더 강력하게 중복을 막지만, 같은 상품이 마감일만 바뀌어 재오픈되는 경우도 새 건으로 안 잡혀 놓치게 된다 |
| 기존 중복 207건을 스크립트로 자동 정리(dry-run 후 실행) | 스크립트가 "같은 상품"을 제목만으로 판단하면 실제로 다른 상품을 잘못 지울 위험이 있다. 사장님이 직접 확인하는 쪽을 골랐다 |

**받아들인 대가** — 기존 중복 207건은 당장 안 지워진다. 관리자가 하나씩 확인해야 한다.

**당시 확신도** — 높음. 실제 서버 데이터로 정확한 원인(시작일 매칭 실패)과 규모(233그룹/469건)를
확인했다. tsc·build·python 문법 검사 클린, 로컬에서 실제 서버 데이터로 관리자 화면에 중복
목록이 정확히 뜨고 "열어보기"가 수정 화면을 여는 것까지 확인함.

## D-069 · 진행 중 카드에서 다른 브랜드 대체 링크를 숨김 · 2026-08-28

**상태:** 유효

**상황** — 사장님이 "공구가 진행 중일 때 쿠팡 파트너스 링크가 다른 브랜드로 걸려있으면
노출하지 말고 끝난 뒤에만 노출해달라"고 요청. 코드를 보니 상세 페이지(`app/post/[id]/page.tsx`)는
이미 D-027로 이렇게 돼 있었는데(진행 중엔 같은 상품 링크만, 그마저도 아쉽딜일 때만),
**공구 카드**(`components/PostCard.tsx`, 홈·카테고리·컬렉션·인플루언서 페이지 전부가 이걸
쓴다)는 등급과 무관하게 `visiblePurchaseLinks(post)`를 그대로 써서 같은 상품·다른 브랜드
대체 링크를 진행 중에도 전부 보여주고 있었다. 실제로 진행 중 공구 14건이 다른
브랜드/비슷한 상품 링크를 카드에 노출 중이었다.

**결정** — `PostCard.tsx`의 대체 링크를 진행 중엔 `sameProductLinks(post)`(같은 상품만),
종료 후엔 `visiblePurchaseLinks(post)`(대체 상품 포함 전부)로 바꿨다. 등급별 노출 제한은
이번엔 안 건드렸다 — 사장님이 요청한 건 "다른 브랜드는 진행 중에 숨겨라"였지 등급 제한이
아니었다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 상세 페이지처럼 등급(아쉽딜만) 제한까지 카드에도 적용 | 사장님이 요청한 범위를 벗어난다. 카드는 원래도 등급 무관하게 같은 상품 링크를 보여줬고, 이번 요청은 "다른 브랜드" 문제만 지적했다 — 등급 제한은 별도로 필요하면 다시 확인하고 진행 |

**받아들인 대가** — 없음. 상세 페이지와 카드의 "진행 중 노출 기준"이 이제 더 가까워졌다
(둘 다 같은 상품만 우선한다).

**당시 확신도** — 높음. tsc·build 클린. 실제 서버 데이터로 다른 브랜드 링크가 걸린 진행
중 공구를 찾아 로컬에서 카드가 안 보이는 것까지 브라우저로 직접 확인함.

## D-068 · 품절도 "공구 끝남"으로 취급 — 기간종료와 같은 경로(ended_at)로 통일 · 2026-08-28

**상태:** 유효

**상황** — 사장님이 "품절로 자동숨김된 공구에 쿠팡 파트너스 링크를 달면 다시 공개되냐"고
물었다. 확인해보니 아니었다 — 기간종료(마감일 지남)는 `status`를 그대로 두고 화면만
"종료됨" 상태로 바꿔서 URL이 살아있고 쿠팡 링크가 있으면 자동으로 「지금 살 수 있어요」로
보여주는데(`D-002`, `D-031`), 품절 자동숨김(`check_links.py`)은 `status`를 `ready`로
내려버려서 상세 페이지 자체가 비공개가 되고, 쿠팡 링크가 있어도 전혀 안 보였다. 사장님은
"품절도 공구가 끝난 것"이라고 확인했다 — 기간종료와 다르게 취급할 이유가 없다.

로직을 다시 검토하다가 관련된 별도 버그를 하나 더 찾았다: 품절로 숨긴 순간 그 공구는
`is_customer_visible()`(점검 대상 판정)에서 제외되는데, 다음 날 점검 대상 목록도 같은
함수로 다시 뽑기 때문에 한 번 숨겨진 공구는 그 이후로 다시는 점검되지 않는다 — 즉
"재입고 시 자동 복구"가 문서에는 있었지만 실제로는 한 번도 동작하지 않았다. 서버 데이터에
품절 태그가 붙은 채 5주 넘게(7/21~) 멈춰 있는 공구가 22건 있었고, 그중 `status: published`로
돌아온 2건은 스크립트가 아니라 사장님이 관리자 화면에서 직접 되돌린 것으로 보였다.

**결정**
- 품절 감지 시 `status`/`published`는 건드리지 않고(`upcoming` 제외) `ended_at`만 찍는다 —
  기간종료와 완전히 같은 경로. `lib/period.ts`의 `isExpired()`가 `ended_at`을 최우선으로
  보므로 자동으로 목록에서 빠지고, `isPagePublic()`은 `status`만 보므로 상세 페이지는
  계속 살아있다. 쿠팡 링크가 있으면 자동으로 「종료됐지만 살 수 있어요」로 보인다.
- 점검 대상 목록에 "지금은 안 보이지만 품절 태그가 붙어 재입고를 기다리는 공구"를
  계속 포함시킨다(`needs_recheck()`). 안 그러면 새 방식도 똑같이 한 번 숨기면 다시는
  못 본다 — 이게 재입고 자동 복구가 실제로 동작하지 않았던 근본 원인이다.
- 예전 방식(`status='ready'`)으로 멈춰 있던 22건은 별도 마이그레이션 스크립트 없이
  `mark_sold_out`/`clear_sold_out` 안에서 함께 정상화한다 — 다음 점검에서 자연히 고쳐진다.
- `upcoming`(오픈 전) 상태는 예외로 남긴다 — `isCustomerVisible`이 `upcoming`일 때
  `ended_at`을 아예 안 보므로("오픈 전인데 종료"는 말이 안 됨), 이 경우만 `published`를
  직접 토글한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 재입고 감지 버그만 고치고 품절-종료 통일은 안 함 | 사장님이 물어본 원래 질문(쿠팡 링크로 재공개되냐)에 대한 답을 그대로 두는 셈이라 요청의 핵심을 놓친다 |
| 품절 전용 새 상태(`sold_out_at` 필드 등)를 따로 둠 | `ended_at`이 이미 "끝난 걸 아는데 날짜를 못 박기 애매한 경우"를 위해 있다(`D-026`). 새 필드를 만들면 `isExpired`·`isCustomerVisible`·화면 문구를 전부 다시 분기해야 하는데, 사장님이 "품절도 끝난 것"이라고 했으니 같은 필드를 쓰는 게 정확하고 단순하다 |

**받아들인 대가** — 관리자 화면에서 품절로 종료된 공구와 마감일이 지나 종료된 공구가
구분 없이 같은 "종료" 취급을 받는다. 왜 종료됐는지는 `review_reason`의
`SOLD_OUT_REASON` 태그로 여전히 구분할 수 있다.

**당시 확신도** — 높음. 사장님이 "품절도 끝난 것"이라고 명시적으로 확인. 로직을 코드로
다시 추적해 재입고 미작동 버그를 실제 서버 데이터(22건 정체)로 확인했고, 합성 데이터로
7가지 상태 전이(정상 품절/재입고, 구방식 마이그레이션 2종, upcoming 품절/재입고)를
전부 단위 테스트로 검증함. 실제 배포 후 다음 cron 실행에서 서버 데이터로 재확인 예정.

## D-067 · 제휴 문의 폼을 이메일·연락처·제휴내용 세 칸으로 줄이고 헤더 메뉴를 /propose로 · 2026-08-27

**상태:** 유효

**상황** — 사장님이 헤더 메뉴의 "내 공구 등록 요청하기"(`/request`)를 "제휴 문의"로 바꿔달라고
요청. `/request`는 구매 링크·가격이 필수인 "이 공구 하나 등록해주세요"용이고, `/propose`는
"우리랑 같이 해볼래요?" 제휴 제안용으로 원래 분리돼 있었다(`D-033`). 사장님 의도는 헤더에서
`/propose`로 보내되, `/propose` 폼 자체도 이메일·연락처·제휴내용만 입력하면 되게 더 간단히
만들어달라는 것이었다.

**결정**
- 헤더 메뉴의 "내 공구 등록 요청하기" 링크를 `/propose`로 바꾸고 문구도 "제휴 문의하기"로
  고쳤다. `/request` 페이지·API는 그대로 남긴다 — 기존 링크(공유됐거나 즐겨찾기된 것)가
  계속 작동해야 한다.
- `/propose` 폼에서 구분(인플루언서/브랜드/업체)·이름·인스타그램·상품 필드를 없애고,
  이메일·연락처·제휴내용 세 칸만 남겼다. `Inquiry` 타입(`lib/inquiries.ts`)도 같이 줄였다
  (`kind`/`name`/`link`/`product` 제거, `email` 추가) — 저장된 문의가 하나도 없어서
  과거 데이터 호환을 신경 쓸 필요가 없었다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|

## D-066 · 공유 이미지에 상품 사진 추가 + 가로형 카드 겹침 버그 수정 · 2026-08-27

**상태:** 유효

**상황** — 사장님이 「꿀딜 확산 후보」 공유 이미지에 상품 사진도 들어갔으면 좋겠다고 요청.
작업 중 로컬에서 실제 데이터로 확인하다가 두 가지를 더 발견했다.
1. 상품명이 2줄로 넘어가는 상품은 가로형(2:1) 이미지에서 상품명 둘째 줄과 "공구가" 줄이
   거의 겹쳐 보였다. 원래부터 있던 버그였다(사진 기능과 무관 — `git stash`로 배포된 코드에서도
   재현됨). `marginTop: 'auto'`로 가격·바닥 블록 위치를 잡고 있었는데, satori가 줄바꿈된
   상품명 박스의 실제 높이를 잘못 측정해 auto 여백이 거의 0으로 계산됐다.
2. 상품명에 개행 문자가 섞인 특정 상품(`766676095`)에서 이미지 생성 자체가 500 에러로
   죽었다 — `width: 조건 ? 500 : undefined`처럼 스타일 값에 명시적 `undefined`를 넣으면
   satori가 파싱 중 죽는다는 걸 확인했다.

**결정**
- 로컬(`/uploads`, `/scraped`)에 저장된 상품 이미지만 파일에서 읽어 base64 data URI로
  박아 넣는다. 외부 URL(인스타 CDN 등)은 satori가 직접 그 사이트에서 받아와야 하는데,
  그 사이트가 느리거나 막혀 있으면 이미지 생성 자체가 실패한다(원칙 1 — 판정 이미지는
  항상 나와야 한다) — 그래서 외부 URL은 지금은 건너뛴다(텍스트만 나간다, 기존과 동일).
- 가로형은 상품명 오른쪽에 168×168 사진을 얹고, 세로형(feed·story)은 상품명 아래 가로
  전체 폭 사진을 넣는다.
- 가로형의 가격·바닥 블록을 `marginTop: 'auto'` 대신 절대좌표(`position: absolute`)로
  고정했다 — 화면 크기가 800×400 고정이라 안전하고, 이걸로 겹침 버그가 없어졌다.
- 스타일 객체에 조건부로 `undefined` 값을 넣지 않는다 — 필요하면 스타일 객체 자체를
  통째로 분기한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 외부 URL 이미지도 satori가 직접 받아오게 허용 | 사이트가 막혀 있거나 느리면 공유 이미지 생성이 통째로 실패한다. 지금 이미지가 있는 상품 대부분(2,415건 중 로컬 204+수집기 저장분)이 로컬 파일이라 당장 아쉬울 게 적다 |
| 겹침 버그는 이번 작업 범위가 아니니 손대지 않는다 | 사진을 얹으려던 바로 그 자리(상품명 옆)에서 발견한 버그이고, 고치지 않으면 새로 만드는 사진 포함 이미지가 여전히 깨져 보인다. 고치는 김에 함께 고쳤다 |

**받아들인 대가** — 외부 URL 상품 이미지는 당분간 공유 이미지에 안 나온다(텍스트만). 나중에
필요해지면 타임아웃을 짧게 건 fetch로 추가하면 된다.

**당시 확신도** — 높음. tsc·build 클린, 로컬에서 실제 데이터(사진 있는 상품·2줄 제목 상품·개행
포함 상품 각각)로 세 비율 모두 직접 생성해 눈으로 확인함.

**결정** — "구매처 클릭"을 계산하는 모든 곳에서 `other`를 뺐다: `/api/analytics`의 `moneyClicks7`, `RevenueBoard`의 `buyerRate`(구매처 클릭률 열), `TodayPriorities`의 `moneyClicks`(퍼널 "구매처 클릭" 단계), `VisitorFlow`의 `totalMoney`와 방문 타임라인의 초록 강조 조건. `other` 클릭 자체는 계속 기록되고 타임라인에도 뜨지만("판매처(제휴없음)"), 돈이 되는 집계에는 안 들어간다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `other`를 완전히 안 보이게 숨김 | 클릭 자체는 실제로 일어난 일이라 기록·타임라인 표시는 남겨야 한다(원칙 1 — 사실을 숨기지 않는다). "돈이 되는 집계"에서만 뺐다 |

**받아들인 대가** — 없음. `other`가 원래도 대부분 D-058 이후 생긴 무제휴 링크뿐이라(옛 데이터의 애매한 alt 링크 소수 제외) 숫자가 줄어드는 효과만 있고, 더 정확해졌다.

**당시 확신도** — 높음. tsc·build 클린. 사장님이 준 정확한 세 범주(대체링크-쿠팡만/쿠팡파트너스/네이버파트너스)를 그대로 코드에 반영했다.

## D-060 · "캘린더에 담기" 클릭이 구매처 클릭으로 잘못 집계되던 버그 수정 · 2026-08-27

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |

**받아들인 대가** — 없음. 버그 수정이라 트레이드오프가 없다.

**당시 확신도** — 높음. tsc·build 클린. 서버 실제 데이터로 재현 확인(post 683546071 "네바 커트러리"가 링크 없이 구매처 클릭률 50%로 뜨는 걸 직접 확인) 후 코드·데이터 양쪽 수정, 수정 후 값 재확인함.

## D-058 · 제휴 없는 판매처 링크 — commission:false + 제휴 재확인 목록 · 2026-08-27

**상태:** 유효

**상황** — 사장님이 "쿠팡 파트너스도 네이버 제휴도 없으면 어떻게 하냐"고 물었다. 조사해보니 **진짜 위험한 문제**가 있었다: 지금 시스템은 `platform`이 coupang이 아니면 링크 도메인을 검증하지 않고, 화면에 뜨는 모든 `purchase_links`에 무조건 "일정액의 수수료를 제공받을 수 있습니다" 공정위 고지를 붙인다(`isAffiliateLink()`가 naver·other는 유효한 URL이면 전부 통과시킴). 실제 제휴가 없는 판매처 링크를 그냥 추가하면 안 받는 수수료를 받는다고 거짓 고지하는 셈이었다.

**결정**
- `PurchaseLink`에 `commission?: boolean`(기본 true, 명시적 false만 "수수료 없음") · `commission_checked_at?: string | null` 추가.

- `RevenueBoard`(수익화 현황)에 세 번째 탭 "제휴 재확인" 추가 — `commission:false` 링크가 붙은 상품을 마지막 확인일이 오래된 순으로 보여준다. 트래픽(조회수) 유무와 무관하게 전부 대상이다(재확인이 목적이라 조회수로 거를 이유가 없다). 행마다 "재확인함"(그대로 없으면 확인일만 갱신)·"제휴 찾았어요"(`PurchaseLinkModal`을 열어 진짜 링크로 교체) 버튼.
- `stripAdminMemo`에 `commission_checked_at` 제거 추가 — 고객 화면엔 쓸모없는 내부 추적용 날짜라서.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `isAffiliateLink()`가 naver/other 도메인도 실제로 검증하게 고침 | 검증할 실제 제휴 도메인 목록이 없다(네이버 제휴 자체가 아직 없다, D-019). 도메인 화이트리스트가 아니라 관리자가 명시적으로 표시하는 쪽이 지금 가진 정보에 맞다 |

**받아들인 대가** — 없음. 기존 `purchase_links` 배열 안에 필드 두 개만 추가한 거라 스키마 변경 폭이 작고, 고지 로직도 함수 하나로 모았다.

**당시 확신도** — 높음. tsc·build 클린, 로컬에서 실제 저장→고객 페이지 렌더링까지 확인(판매처 링크는 보이고 고지 문구는 안 붙는 것, `commission_checked_at`이 고객 페이지 소스에 안 새는 것 둘 다 직접 확인).

## D-057 · 확산 후보 — DM 대신 "우리 채널에 올려두기"로 방향 전환 · 2026-08-26

- 추적링크의 `utm_source`를 `influencer_dm`에서 `kakao_channel`로 바꿨다(실제로 쓰는 채널에 맞춘 값).

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|

**당시 확신도** — 높음. tsc·build 클린, 로컬에서 배치 문구 복사·라벨 변경 확인.

## D-056 · 관리자에 「인플루언서 확산 후보」 화면 추가 · 2026-08-26

**상태:** → "1:1 DM 문구" 부분은 D-057로 뒤집힘 (필터·정렬·이미지·상태관리 구조는 유효)

**상황** — 사장님이 "오늘 누구에게 연락하지?"를 매번 고민하지 않도록, 조건에 맞는 상품을 자동으로 추려 하루 5~10건만 보여주는 화면을 요청. 조건: 진행 중 + 가격비교 완료 + 꿀딜/괜찮딜 + 인플루언서 계정 있음. 정렬은 할인폭 → 반응(조회+클릭) → 아직 연락 안 한 것 순. 행마다 공유 이미지·DM 문구·추적링크 액션과 미전달/전달완료/공유확인/유입발생 상태 관리를 요청했다. 핵심 원칙: **아쉬운딜은 절대 보내지 않는다** — "홍보해 주세요"가 아니라 "가격을 확인해봤는데 정말 좋은 딜이라 알려드립니다"로 접근해야 인플루언서·판매자에게 꿀공구가 광고 매체가 아닌 가격 검증 서비스로 보인다.

**결정**
- 관리자에 새 탭 「인플루언서 확산」(`OutreachBoard`). 조건 필터: `isCustomerVisible && !isExpired && post.influencer_name` (인플루언서 계정) + `getDealVerdict().display.key`가 `honey`/`good`일 때만(가격비교가 끝나야 등급이 나오므로 "가격비교 완료"는 등급 필터에 자동으로 포함된다).
- 정렬: ① `discountRate` 내림차순 ② (상세조회+공구클릭) 내림차순 ③ `outreach_status`가 `none`인 것 우선.
- **공유 이미지**: 새로 안 만든다. 이미 있는 `/api/og/deal/[id]`(가격 비교·판정이 그려진 카카오 공유용 이미지, 카카오 피드 2:1 비율)를 여는 링크만 붙였다.
- **DM 문구**: "가격을 확인해봤는데... 진짜 좋은 딜"이라는 사장님이 준 톤을 그대로 템플릿화해 클립보드에 복사한다. 상품명·할인율·추적링크가 자동으로 채워진다.
- **추적링크**: `?utm_source=influencer_dm&utm_medium=referral&utm_campaign={계정}` — 기존 유입 경로 추적(D-016)이 그대로 잡는다. 새 추적 인프라를 안 만들었다.
- `Post`에 `outreach_status`(`none`/`sent`/`confirmed`/`converted`)·`outreach_updated_at` 추가. PATCH·PUT 허용목록 양쪽에 등록. `toPublicPost`의 관리자 전용 필드 목록(D-044)에도 추가해 고객 화면·API로 안 새게 막았다(실제로 확인함 — `/api/posts`(비관리자) 응답에 필드 자체가 안 잡힘).
- 기본 화면은 "오늘 후보"(미전달 상위 10건)만 보여주고, "전체" 토글로 이미 연락한 것까지 다 본다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 공유 이미지를 이 화면에서 새로 생성 | `/api/og/deal/[id]`가 이미 가격·판정이 그려진 이미지를 만들고 있다. 똑같은 걸 새로 만들면 두 이미지가 어긋날 위험만 생긴다 |
| 아쉬운딜·판정 대기도 후보에 포함(관리자가 걸러내게) | 사장님이 원칙으로 명확히 선을 그은 부분이다("절대 보내지 마세요") — 필터 단계에서 아예 못 나오게 막는 게 실수를 원천 차단한다 |
| DM 발송·전송 상태를 자동화(실제 DM 전송 API 연동) | 요청 범위가 "상태만 체크"였다. 인스타 DM을 대신 보내는 건 별개의 큰 작업이고 계정 정지 위험까지 있다 — 사람이 직접 보내고 상태만 기록하는 걸로 좁혔다 |

**받아들인 대가** — "가격비교 완료" 여부를 별도 플래그로 확인하지 않고 등급(`honey`/`good`)으로 갈음했다. 이론상 등급이 없어도(pending) discountRate가 계산될 수 있는 경로가 있다면 놓칠 수 있지만, 코드 확인 결과 `discountRate`는 등급이 매겨질 때만 채워지므로 실제로는 안전하다.

**당시 확신도** — 높음. tsc·build 클린, 로컬에서 실제 서버 데이터(52건 후보, 마리에뜰 등 실제 인플루언서)로 목록·정렬·복사 버튼·상태 변경(PATCH 왕복)까지 확인. 고객 API에 필드가 안 새는 것도 직접 확인함.

## D-055 · 가격·마감상태 변경 시 sitemap lastmod 갱신 + IndexNow 통보 · 2026-08-26

**상태:** 유효

**상황** — 사장님이 공구 신규등록·가격변경·마감상태 변경 때 sitemap의 `lastmod`를 정확히 갱신하고, IndexNow로 검색엔진에 바로 알려달라고 요청. 기존 sitemap은 `scraped_at`(수집기가 마지막으로 훑은 시각)을 `lastmod`로 썼는데, 관리자가 직접 고친 가격·마감일은 이 값이 안 바뀌어서 다음 수집 전까진 "안 바뀐 것"으로 보였다.

**결정**
- `Post`에 `updated_at` 필드 추가 — 가격·마감일·공개 여부·상태 중 하나라도 바뀌면 서버가 직접 찍는다(클라이언트가 보내는 값이 아니라 PATCH·PUT 핸들러가 계산).
- `app/sitemap.ts`의 `/post/[id]` 항목은 `updated_at || scraped_at`을 `lastmod`로 쓴다.
- 새 `lib/indexnow.ts` — `pingIndexNow(urls)`가 https://api.indexnow.org/indexnow (빙·네이버 등이 공유하는 프로토콜)에 통보한다. 소유 확인용 키 파일은 `public/<key>.txt`에 정적으로 둔다(키는 비밀값이 아니라 소유 확인 토큰이라 코드에 그대로 둬도 된다).
- `/api/posts/[id]` PATCH·PUT, `/api/posts`(신규 등록) POST에서 `price`·`deadline`·`published`·`status`·`ended_at` 중 하나라도 바뀌고 그 결과가 `isPagePublic`이면 통보한다. 실패해도 조용히 넘어간다 — 저장 자체를 막을 이유가 아니다.
- 파이썬 수집기는 건드리지 않는다 — 수집만으로는 고객 화면이 안 바뀐다(검수 대기로 들어갈 뿐). 실제로 고객에게 보이게 되는 순간은 항상 관리자가 발행(PATCH)할 때다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 제목·이미지 등 모든 필드 변경에 통보 | IndexNow는 "정말 바뀐 것"을 알리는 신호다. 사소한 수정까지 매번 보내면 가격·마감처럼 정말 중요한 변경의 신호가 묻히고, 무료 API를 과도하게 두드리게 된다 |
| IndexNow 응답을 기다렸다가 저장 완료 처리 | 외부 API가 느리거나 죽으면 관리자 저장(가장 중요한 동작)까지 함께 느려지거나 실패한다. 응답을 기다리지 않고 쏘기만 한다 |

**받아들인 대가** — IndexNow는 "알림"일 뿐 색인을 보장하지 않는다. 실제 반영 여부는 검색엔진 대시보드에서만 확인 가능하다(원칙 2 — 반영됐다고 단정하지 않는다).

**당시 확신도** — 높음. tsc·build 클린, 로컬에서 키 파일 서빙·sitemap lastmod 로직 확인. 실제 IndexNow 통보 성공 여부는 배포 후 실제 변경이 일어나야 확인 가능(로컬에서 실제 API를 두드리는 테스트는 하지 않았다).

## D-054 · 개별 상세·랜딩 페이지 제목을 검색어에 맞춰 다시 씀 · 2026-08-26

**상태:** 유효

**상황** — 사장님이 페이지 제목이 실제 검색어와 안 맞는다고 지적. 예: 상품 상세 제목이 "가격 및 기간"처럼 사이트 내부 용어였고, 카테고리·인플루언서·오늘공구·마감임박 페이지도 부제가 길어 검색 결과에서 잘리거나 자연스러운 검색어와 안 겹쳤다.

**결정** — 5개 페이지 제목을 다시 썼다: `/post/[id]`, `/today`, `/deadline`, `/category/[cat]`, `/influencer/[account]`.
- `/post/[id]`: `{상품명} 공구 {가격}원 | 가격비교` — "가격비교"는 실제 비교가가 있을 때만 붙인다(`getDealVerdict().display.key !== 'pending'`). 마감 후엔 `| 마감 후 구매처`.
- `/category/[cat]`: `{라벨} 공동구매 · {동의어} 공구 모아보기` — 동의어는 카테고리 뜻과 실제로 겹치는 것 하나씩만(유아동→육아, 생활→생활용품, 식품→먹거리, 건강→헬스케어, 뷰티→화장품). 관련 없는 인기 키워드는 안 넣는다(네이버 서치어드바이저 안내 — 억지로 넣으면 오히려 불리하다).
- `/influencer/[account]`: `{이름} 공동구매 일정·진행중 공구 모아보기`.
- `/deadline`: `마감 임박 공동구매 모아보기 — 3일 안에 끝나는 공구`.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `/deadline` 제목에 "오늘 마감"을 그대로 씀(사장님 예시 원문) | 이 페이지는 "3일 안에 마감"이 실제 조건이라, "오늘 마감"이라고 쓰면 1~3일 뒤 마감인 공구까지 오늘 마감인 것처럼 읽혀 틀린 말이 된다(원칙 1) |
| 인플루언서 검색 수요가 강할 때 제목에서 브랜드명 대신 인플루언서 이름을 우선 노출(사장님이 예시로 든 두 번째 안) | "검색 수요"를 판단할 실제 키워드 볼륨 데이터가 없다 — 확신 없이 조건 분기를 만들면 원칙 2에 어긋난다. 대신 상품 상세 제목은 항상 상품명 기준으로 고정하고, 인플루언서 이름은 `/influencer/[account]` 페이지 자체에서 이미 전면에 쓴다 |

**받아들인 대가** — 카테고리 동의어(육아·먹거리 등)가 실제로 검색 유입을 늘리는지는 네이버 서치콘솔 데이터가 쌓여야 확인 가능하다. 지금은 근거 있는 추정이다.

**당시 확신도** — 중간. tsc·build 클린, 로컬에서 5개 페이지 `<title>` 실제 렌더링 확인. 키워드 선택 자체(어떤 동의어가 실제로 검색 유입을 늘리는지)는 검색 콘솔 데이터로 검증된 바 없다.

## D-053 · 성장 목표 카드에 "늘면 열리는 기능"과 지난주 대비 추이 추가 · 2026-08-26

**상태:** 유효

**상황** — D-052까지 고친 뒤 사장님이 "성장 중인 느낌이 안 들고, 1단계를 완료하면 다음에 뭘 할지 안 적혀 있어 애매하다"고 지적. 두 가지로 좁혔다: ① 42%라는 정적인 숫자만 있어 지금 오르는 중인지 멎어 있는지 안 보인다 ② 단계를 넘으면 무엇이 달라지는지가 안 보인다.

- **추이**: "7일 평균" 카드에 그 전 7일 대비 증감(▲+48 / ▼-N)을 작게 붙인다. `getSummary(14)`가 이미 14일치를 주므로 `analytics.slice(-14,-7)`이 곧 "그 전 7일"이다 — 새 API 호출이 없다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 6단계 성장 사다리(150→...→10,000)에 맞춰 새 액션 항목을 6개 만듦 | 사장님이 무엇을 할지 아직 정한 적 없는 단계(500·1,000·3,000·10,000)에 억지로 액션을 지어내면 원칙 2(확신 없이 말하지 않는다)에 어긋난다. 이미 결정된 것(D-029 근처 키워드 알림·댓글 기능 보류 조건)만 정직하게 연결했다 |
| 키워드 알림 기준(일 100명)을 단계 사다리 중 가장 가까운 값(150, 1단계)에 맞춰 반올림 | 100과 150은 다른 숫자다. 사다리에 억지로 끼워 맞추면 "1단계를 완료해야 열린다"는 틀린 인상을 준다 — 실제로는 100명 시점에 이미 조건을 만족한다. 사다리와 별개 목록으로 뒀다 |

**받아들인 대가** — 없음. 기존 데이터(`analytics`, `CLAUDE.md`의 기존 결정)를 다시 보여주는 것뿐이라 새 데이터도, 새 결정도 추가되지 않았다.

**당시 확신도** — 높음. tsc·build 클린, 로컬 브라우저에서 실제 서버 데이터로 추이 화살표·잠금해제 목록 렌더링 확인.

## D-052 · 성장 목표 카드 — 6단계 전부 대신 지금 단계 하나만 크게 · 2026-08-26

**상태:** 유효 (D-051의 "6단계 전부 표시" · "현재 단계=마지막으로 넘은 단계" 두 가지를 뒤집음)

**상황** — D-051을 실제로 보고 사장님이 두 가지를 지적했다. ① "현재 단계"가 150명을 넘어야만 "1단계"로 뜨고 그 전엔 "시작 전"이라 나와 혼란스러웠다(이건 먼저 한 번 "N단계 도전 중"으로 고쳤었다). ② 6단계 진행률 바를 한 화면에 다 펼치니 지금 63명이 10,000명 옆에서 너무 작아 보여 부담스럽다 — "10,000명까지 1% 왔다"가 아니라 "1단계의 42%까지 왔다"가 지금 필요한 정보라고 짚었다.

**결정**
- 상단 요약을 4칸으로: 7일 평균 · 7일 합계 · 구매처 클릭(7일) · **구매처 클릭률(7일)**(신규 — `moneyClicks7 / week7 × 100`). "사람이 늘었나 · 구매 행동도 같이 늘었나"를 한 화면에서 보게 한다.
- 6단계 바 목록을 없애고, **지금 도전 중인 단계 하나만** 크게 보여준다 — "N단계 · 일평균 X명" 제목 + "63명 / 150명 · 42%" + 큰 바 하나 + "N단계 달성까지 평균 +88명".
- 그 아래 남은 단계는 숫자만 작게 나열한다: "다음: 300명 → 500명 → 1,000명 → 3,000명 → 10,000명" — 존재는 보이되 시선을 뺏지 않는다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 6단계 바를 유지하되 크기만 줄임 | 사장님이 짚은 문제의 본질은 "여러 목표가 동시에 보이는 것" 자체다. 작게 줄여도 지금 단계가 몇 번째 바인지 찾아야 하는 건 그대로다 |
| 클릭률을 나중으로 미룸 | 계산식이 이미 있는 두 숫자(`moneyClicks7`, `week7`)의 나눗셈이라 비용이 거의 없고, 사장님이 구체적인 이름("구매처 클릭률")까지 줬다 — 미룰 이유가 약했다 |

**받아들인 대가** — 없음. 표시 방식만 바뀌었고 데이터 구조·API는 그대로다.

**당시 확신도** — 높음. tsc·build 클린, 실제 서버 데이터(7일 평균 63명)로 로컬 브라우저 렌더링 확인.

## D-051 · 관리자 대시보드에 성장 목표(일 방문자 단계) 카드 추가 · 2026-08-26

**상태:** → "6단계 전부 표시"·"현재 단계 판정" 부분은 D-052로 뒤집힘 (그 외 구조는 유효)

**상황** — 사장님이 관리자 대시보드에 일 방문자 기준 성장 단계(150→300→500→1,000→3,000→10,000)를 두고, 각 단계 달성률을 프로그레스 바로, 현재 단계·다음 단계까지 남은 수치·최근 7일 방문자 추이를 함께 보여달라고 요청. 단계 숫자는 나중에 관리자에서 고칠 수 있어야 한다고 했다.

**결정**
- 새 데이터 파일 `data/growth_goals.json`(`{stages: number[]}`, 기본값 요청받은 6단계) + `lib/store.ts`의 `loadGrowthGoals`/`saveGrowthGoals`.
- 새 API `/api/growth-goals` — GET/PUT 모두 관리자 전용(미들웨어 `isProtected`+`config.matcher` 양쪽 등록). PUT은 단계가 전부 양수이고 오름차순인지 서버에서 검증한다.
- `/api/analytics` GET 응답에 `moneyClicks7`(최근 7일 쿠팡·네이버·기타 클릭 합) 필드 추가 — 이미 있는 `getClickCounts()`를 재사용, 새 집계 로직 없음.
- `app/admin/page.tsx`에 `GrowthGoalsBoard` 컴포넌트 추가. "오늘 손보면 돈 되는 일"과 "방문자 분석" 사이, 탭과 무관하게 항상 보이는 자리에 둔다(둘 다 같은 성격의 "대시보드 요약" 카드라서).
- **"현재 단계"는 오늘 하루 방문자가 아니라 최근 7일 평균으로 정한다.** 요일 편차(주말 vs 평일)가 커서 하루 값을 기준으로 하면 좋은 날 하루로 다음 단계를 넘긴 것처럼 보이거나, 나쁜 날 하루로 이미 넘은 단계 아래로 떨어져 보인다 — 단계 판정이 매일 출렁이면 "지금 어디쯤인지"에 대한 신뢰가 떨어진다.
- 단계별 진행률 바는 6개 전부 표시한다(사장님이 "각 목표 달성률"이라고 복수로 요청) — 다음 단계 하나만 보여주는 대신 전체 사다리를 한눈에 보게 했다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 오늘 방문자 수를 기준으로 현재 단계 판정 | 사장님이 명시한 "일 방문자"를 가장 문자 그대로 따르는 방식이지만, 하루 방문자가 30~95명 사이로 3배씩 뛰는 게 실측으로 확인됐다(8/20~8/26). 매일 단계가 왔다갔다 하면 성장 추적 지표로서 신뢰를 잃는다 — 7일 평균이 더 안정적이다 |
| 주간 방문자·구매처 클릭 수에도 각각 자체 목표 사다리를 만듦 | 사장님이 준 단계 숫자(150→...→10,000)는 명시적으로 "일 방문자" 기준이다. 다른 두 지표에 목표를 매기려면 숫자를 새로 지어내야 하는데, 근거 없는 목표를 만들면 원칙 2(확신 없이 말하지 않는다)에 어긋난다. 두 지표는 참고 숫자로만 옆에 보여준다 |
| 성장 목표를 "채우기"처럼 별도 탭으로 뺌 | "오늘 손보면 돈 되는 일"·"방문자 분석"과 같은 급의 대시보드 요약이라, 탭 뒤에 숨기면 사장님이 매번 클릭해서 찾아가야 한다 |

**받아들인 대가** — 없음. 기존 집계 함수(`getSummary`, `getClickCounts`) 재사용이라 새 수집 로직이 없고, 데이터 스키마도 파일 하나(`growth_goals.json`) 추가뿐이다.

**당시 확신도** — 높음. tsc·build 클린, 로컬 브라우저에서 서버 실제 데이터로 진행률 바·현재 단계·다음 단계 수치·7일 추이 차트 렌더링 확인, 단계 수정(PUT) 저장→재조회 왕복까지 실제로 테스트.

## D-050 · 수익화 현황 표에 상품별 클릭률 열 추가 · 2026-08-26

**상태:** 유효

**상황** — 사장님이 관리자 "수익화 현황" 표에서 상세조회 대비 구매클릭 비율을 상품별로 보고 싶다고 요청. 상세조회/공구 클릭/쿠팡/네이버는 이미 `getClickBreakdown()`(analytics.ts)이 상품별로 집계해 두고 있었고, `RevenueBoard` 표에도 이미 컬럼으로 있었다 — 없던 건 "클릭률" 하나뿐이었다.

**결정** — `RevenueBoard`의 `rows` 계산에 `ctr = (공구클릭+쿠팡+네이버) / 상세조회 × 100` 을 추가하고 표에 열을 넣었다. 20% 이상이면 초록색으로 강조한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 클릭률 = (쿠팡+네이버)/상세조회 (돈 되는 클릭만) | 표 상단 설명이 이미 "돈이 되는 건 쿠팡·네이버뿐"이라고 별도로 짚어준다. 클릭률까지 그 기준으로만 재면 공구 클릭만 있는 상품(꿀딜 등, 대체 구매처를 일부러 안 붙인 것 — D-027)이 전부 0%로 보여서 "이 상품은 반응이 없다"는 착시가 생긴다. 클릭률은 "상세조회가 실제 이탈(어디로든 나감)로 이어지는지"를 보는 지표로 두고, 돈이 되는지는 쿠팡·네이버 열을 따로 보게 했다 |

**받아들인 대가** — 없음. 이미 있는 집계 함수에 표시 컬럼 하나를 얹은 것뿐이라 새 데이터 수집이나 스키마 변경이 없다.

**당시 확신도** — 높음. tsc·build 클린, 서버에서 내려받은 실제 analytics.json/posts.json으로 로컬에서 표 렌더링(0.0%~100.0% 범위, 정렬·강조 포함) 확인.

## D-048 · 컬렉션 배너를 여러 장 넘기는 캐러셀 구조로 미리 바꿔둠 · 2026-08-26

**상태:** 유효

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|

## D-047 · nav는 로고·검색까지만 — 배너·카테고리는 스크롤에 묶지 않는다 · 2026-08-26

**상태:** 유효 (D-046의 "스크롤하면 카테고리가 햄버거로 접힌다" 부분을 뒤집음 → D-046 참고)

**상황** — D-046에서 구현한 "스크롤 내리면 카테고리 그리드가 햄버거 버튼으로 접힌다" 동작을 사장님이 실제로 보고 두 번 고쳐달라고 했다. ① 햄버거가 카테고리 있던 자리(화면 중간)에 나타나 어색하다 — 보통 메뉴 버튼처럼 왼쪽 위에 있어야 한다. ② 사장님이 준 쿠팡 실제 스크린샷 기준으로 보니, 애초에 "카테고리를 접는다"는 방향 자체가 참고 화면과 다르다 — 쿠팡은 검색창까지만 고정 nav이고, 그 아래 롤링 배너·카테고리 그리드는 그냥 스크롤되어 넘어가는 본문이다. 햄버거도 나타났다 사라지는 게 아니라 늘 같은 자리에 있어서 로고가 밀리지 않는다.

**결정**
- `categoryCollapsed` 상태와 그 `scroll > 80` 리스너를 완전히 없앤다. 카테고리 그리드·꿀픽 배너는 더 이상 스크롤 위치에 따라 나타났다 사라지지 않는다 — 그냥 본문(body)의 일부로 늘 렌더링되고 스크롤을 따라 자연스럽게 넘어간다.
- `.app-header`(sticky)에는 로고·오른쪽 아이콘들이 있는 `Header`와 검색창만 남긴다. 카테고리 드롭다운을 여는 햄버거 버튼은 `Header.tsx`의 `.header-inner` 첫 자리에 **항상** 렌더링한다(조건부 아님) — `categoryCollapsed` prop 자체를 없앴다.
- 카테고리 드롭다운 패널은 여전히 `.app-header`의 자식으로 두고 `position:absolute; top:100%`를 쓴다(이전 턴에 고친 sticky-containing-block 방식 그대로) — 버튼이 상시 존재해도 패널이 "nav 바로 아래"에 뜨는 동작은 그대로 맞다.
- 꿀픽 배너(`.collection-banner`)는 더 이상 `.app-header` 안에서 헤더 여백 기준으로 배치되지 않으므로, 본문 다른 섹션(`.category-wrap`)과 같은 자기-중앙정렬 방식(`width: calc(100% - 40px); max-width: 640px; margin: 16px auto`)으로 바꾼다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 햄버거만 Header로 옮기고 스크롤 접힘 로직은 유지 | 1차 피드백만 반영한 것으로, 실제로 배포 전 2차 피드백(쿠팡 스크린샷 비교)에서 "접힘" 방향 자체가 틀렸다고 확인됨 |
| 배너·카테고리를 여전히 sticky 영역 안에 두되 높이만 줄임 | 사장님이 명시적으로 "nav로 묶이면 안 된다"고 했다 — sticky 영역 안에 있으면 스크롤할 때마다 화면 위쪽을 계속 차지하는 문제가 근본적으로 남는다 |

**받아들인 대가** — 없음. D-046보다 참고 화면(쿠팡)에 더 가까워졌고, 레이아웃 시프트가 사라졌다.

**당시 확신도** — 높음. tsc·build 클린, 로컬 브라우저로 상단/스크롤 상태 모두 스크린샷 확인(진짜 모바일 폭은 이 세션 도구 제약으로 CSS 강제 주입 방식으로 확인 — D-046과 동일한 한계).

## D-046 · 홈 화면을 쿠팡 스타일로 정리 — 아이콘 제거·카테고리 그리드·컬렉션 배너 · 2026-08-25

**상태:** → 스크롤 접힘 부분은 D-047로 뒤집힘 (아이콘 그리드·구분선·컬렉션 배너 자체는 유효)

**상황** — 사장님이 모바일 홈 화면을 쿠팡처럼 정리해달라고 요청. 네 가지: ① 섹션 제목 앞 아이콘을 빼고 구분선으로 대체 ② "꿀픽" 컬렉션을 배너 형태로 섹션 중간에 ③ 카테고리를 쿠팡 카테고리(아이콘 그리드)처럼 ④ 스크롤하면 카테고리가 햄버거 버튼으로 접힘. ③은 "아이콘 그리드형"과 "지금 가로 스크롤 유지"를 preview로 보여드리고 아이콘 그리드형으로, ④의 배너 위치는 "3번째 섹션 뒤"로 확인받았다.

**결정**
- 모바일(640px 이하)에서 `.strip-title`의 아이콘 svg를 숨기고, 섹션 사이 구분선을 8px 굵은 회색 바로 강화한다.

- 카테고리 스크롤 접힘: `window.scrollY > 80`에서 카테고리 그리드 대신 햄버거 버튼을 보여주고, 누르면 같은 `CategoryFilter`를 드롭다운 오버레이로 띄운다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 카테고리를 모바일 전용 별도 컴포넌트로 새로 만듦 | 실제 카테고리 이동 로직(Link vs button, D-041의 스크롤 이동)을 그대로 복제해야 한다. 마크업 하나 + 미디어쿼리로 스타일만 가르는 쪽이 로직 중복을 없앤다 |
| 컬렉션 배너도 클라이언트에서 상품 이미지까지 가져와 보여줌 | 배너 한 장에 여러 상품 이미지를 보여줄 이유가 없다(원래 롤러가 하던 일). 컬렉션 메타만 쓰면 클라이언트 fetch·상태·자동회전 로직이 통째로 필요 없어진다 — `CollectionRoller.tsx`를 지웠다 |
| 활성 컬렉션이 여럿일 때를 미리 대비해 배너 여러 장을 순서대로 배치 | 지금 활성 컬렉션이 1개뿐이다(실측). 여럿이 될 때 다시 본다 — 없는 요구를 미리 설계하지 않는다 |

**받아들인 대가** — 컬렉션이 2개 이상 활성화되면 첫 번째만 배너로 보이고 나머지는 홈에서 안 보인다. 지금은 해당 사항 없다.

**당시 확신도** — 높음. 실제 모바일 폭(390px)으로는 이 세션의 브라우저 도구가 리사이즈가 안 돼서(최소 폭 제한, 이전에도 겪은 문제) 진짜 좁은 화면으로는 못 봤다 — 대신 페이지에 임시 CSS를 주입해 그리드·배너·햄버거 드롭다운 동작을 시각적으로 확인했다. 실제 폰 확인을 권한다.

## D-045 · 마감 상세 페이지는 "판단"이 아니라 "다음 구매"가 목적이다 · 2026-08-25

**상태:** 유효

**상황** — 사장님이 상세 기획서를 줬다. 핵심 질문: "이 공구는 끝났는데, 지금은 어떻게 사면 되지?" 마감 페이지가 진행 중 페이지와 같은 구조(판정 카드가 화면 대부분을 차지)를 그대로 쓰고 있어서, 정작 급한 정보(지금 어디서 사나)가 카드들 사이에 묻혀 있었다.

**결정** — 마감 페이지에만 적용한다(진행 중·아쉽딜은 그대로 둔다 — 사장님 확인). 우선순위를 코드로 그대로 옮긴다: ① 마감 사실 ② 당시 가격+할인율 한 줄 ③ 지금 구매 가능한 곳 ④ 동일/대체 상품 ⑤ 판정 상세(접어 둠) ⑥ 공유.

- `EndedDealNotice`: "당시 공구가" 옆에 `getDealVerdict()`가 계산한 할인율을 한 줄로 붙인다(원칙: 할인율은 항상 여기서만 계산한다, D-014). 대체 상품 영역 제목을 relation별로 구체화한다("비슷한 상품도 찾아봤어요" 등, "이런 건 어때요?" 같은 뭉뚱그린 말 대신). 각 대체 상품 카드에 관계 배지("비슷한 상품 · 동일 상품 아님")를 붙인다.
- `PostCard`에 `endedCompact` prop을 추가한다. 마감 페이지에서만 켠다 — 가격·판정 카드를 다시 그리지 않고 "가격 비교 자세히 보기"로 접어 둔다(같은 정보가 위 요약과 아래 판정 카드 두 번 나오던 걸 없앤다). 마감 상태에서 이미지·제목·기간 줄(마감됨)은 그대로 남긴다.
- CTA 문구를 "N원에 구매하기" → "N원에 지금 보기"(동일 상품), "OO에서 비교해보기" → "비슷한 상품 보기"(대체 상품)로 바꾼다.

**부수 발견** — 구현 확인 중 실제 버그를 하나 찾았다: `periodTextFromState()`가 `deadline_unknown` 상태를 항상 "진행 중"으로 표시하고 있었다 — `isExpired()`는 21일(`DEADLINE_UNKNOWN_DAYS`)이 지나면 마감으로 보는데, 이 표시 함수는 그 판단을 안 봐서 상세 페이지 맨 위는 "종료됐어요"인데 카드 안 기간 줄은 "진행 중"이라고 서로 다른 말을 하고 있었다. `state.daysSince`로 같은 기준을 적용해 "마감됨"으로 고쳤다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| PostCard를 그대로 두고 EndedDealNotice만 위에 요약을 더 얹음 | 같은 가격·판정 정보가 화면에 두 번(요약 + 카드) 나온다 — 정확히 사장님이 지적한 "화면이 길고 어디를 눌러야 할지 분산된다"는 문제를 그대로 남긴다 |
| 마감 전용으로 새 카드 컴포넌트를 통째로 새로 만듦 | PostCard는 이미지·배지·공유·찜 등 로직이 많다. 새로 만들면 그 로직을 전부 복제해야 하고, 나중에 한쪽만 고치는 버그가 생긴다. `endedCompact` prop으로 필요한 부분만 접는 쪽이 안전했다 |

**받아들인 대가** — 없음(기존 컴포넌트 확장이라 라이브 페이지 구조를 크게 바꾸지 않았다).

**당시 확신도** — 높음. 로컬에서 서버 실데이터(같은 상품 예시·대체 상품 예시 둘 다) 주입해 브라우저로 직접 확인 — 요약·CTA·접이식 판정 카드·"마감됨" 일관성까지 확인했다.

## D-044 · 관리자 전용 필드를 고객 화면 페이지 소스에서도 지운다 · 2026-08-25

**상태:** 유효

**상황** — D-043에서 대체 상품의 관리자 메모(`adminMemo`)가 화면엔 안 보이는데 페이지 소스(뷰소스/RSC payload)엔 그대로 남아있는 걸 발견했다. Next.js는 서버 컴포넌트가 클라이언트 컴포넌트에 넘기는 props를 페이지 소스에 그대로 직렬화한다 — 화면에 안 그려도 "보기 소스"로 다 보인다. 확인해보니 `adminMemo` 하나만의 문제가 아니었다: `review_reason`(검수 사유)·`compare_none_reason`/`compare_none_note`(비교불가 판단)·`extraction_debug`(원문 스크래핑 조각 전체)·`market_price_note`·옛 `partners_*` 필드까지 전부 같은 경로로 새고 있었다. 코드 주석에 "고객 화면은 이 값을 쓰지 않는다. 검수 상태는 우리 사정이다(원칙 3)"라고 이미 적혀 있던 필드들인데, 화면에 안 그린다는 것과 소스에서 지운다는 것을 같은 걸로 착각하고 있었다.

**결정** — `lib/publicPost.ts`에 `toPublicPost()`(denylist 방식)를 만들어 고객 화면으로 가는 모든 경로의 끝(`lib/landing.ts`의 `visiblePosts()`/`endedButBuyablePosts()`, `/api/posts`·`/api/collections/[id]` GET의 비관리자 응답, `/post/[id]`·`/collection/[id]` 페이지)에 적용한다. `extraction_debug`는 통째로 지우지 않는다 — `PostCard`의 "가격·마감일 확인된 정보예요" 배지가 `extraction_confidence` 하나만 읽어서, 그 값만 남기고 나머지(원문 후보값 전체)는 지운다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| allowlist(필요한 필드만 명시)로 짬 | `Post` 필드가 50개 가까이 되고 대부분 `getDealVerdict`·`getPeriodState`가 클라이언트 컴포넌트 안에서도 계산에 쓴다. 하나라도 빠뜨리면 화면이 조용히 깨진다 — 뺄 것만 정하는 denylist가 더 안전했다 |
| `adminMemo`만 딱 고침 | 사장님이 "화면 노출만 막으면 뭐해"라고 직접 지적 — 같은 구조의 문제가 다른 필드에도 이미 있었고(주석에 "고객 화면은 안 쓴다"고 적힌 필드들), 하나만 고치면 곧 또 재발한다 |

**받아들인 대가** — 새 관리자 전용 필드를 추가할 때마다 `lib/publicPost.ts`의 목록에도 같이 넣어야 한다 — 안 넣으면 다시 샌다. `app/api/posts/[id]/route.ts`의 allowlist(저장용)와는 반대 방향(노출용)이라 헷갈리지 않게 문서화해 둔다.

**당시 확신도** — 높음. 로컬에서 `/api/posts`·`/post/[id]` 응답을 직접 떠서 `adminMemo`·`review_reason`·`compare_none_*`·`partners_*`가 전부 사라진 것과 `extraction_debug`가 `extraction_confidence`만 남긴 것 확인.

## D-043 · 대체 상품 링크에 "관계 3단계"와 관리자 전용 메모를 추가한다 · 2026-08-25

**상태:** 유효

**상황** — 대체 상품 링크(D-030/D-031)는 "같은 상품 vs 다른 상품" 이분법이었다. 사장님이 상세 스펙으로 요청: (1) 동일 상품/같은 브랜드 다른 상품/비슷한 상품 세 단계로 나누고 (2) 관계별 기본 문구를 자동으로 채우되 수정 가능하게 하고 (3) 상품명을 별도로 보여주고 (4) "브랜드가 달라요, 팩토는 어때요" 같은 내부 판단 메모는 고객 화면에 안 나가게. 확인해보니 (4)는 실제로 이미 사고였다 — `note` 필드가 관리자 내부 메모 용도로 쓰이고 있었는데 고객 화면(`EndedDealNotice`)에 그대로 렌더링되고 있었다. "곰탕" 공구 등 실제 라이브 페이지에서 "브랜드가 달라요" 문구가 그대로 노출되고 있는 걸 확인했다.

**결정** — 스키마를 최소로 확장한다. 기존 `kind: 'same'|'alternative'`(판정 가드레일, `isSameProduct()`가 그대로 씀)는 안 건드리고, `relation: 'same'|'same_brand'|'similar'`을 새로 추가해 `relation`이 `kind`를 자동으로 결정하게 한다(`same`→`kind:same`, 나머지→`kind:alternative`). `productName`·`reason`(고객 노출)을 새로 추가하고, 관리자 내부 메모는 `note`를 재활용하지 않고 `adminMemo`라는 새 필드로 분리했다 — `note`는 원래 뜻(동일 상품의 옵션 참고사항, 고객 노출)을 그대로 유지한다. `reason`은 `relation` 선택 시 기본 문구(`RELATION_DEFAULT_REASON`)로 자동 채워지고, 관리자가 고친 문구는 relation을 바꿔도 안 덮어쓴다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `note`를 관리자 전용으로 재정의 | `note`는 지금도 "동일 상품" 링크의 옵션 참고 문구로 정상적으로 고객에게 보여지고 있었다(예: "2개입 기준"). 그 용도를 없애면 관련 없는 회귀가 생긴다 — `adminMemo`를 새로 만드는 게 더 안전했다 |
| `kind`를 3단계로 늘림 | `isSameProduct()`·`sameProductLinks()`·`hasPurchaseLink()` 등 판정 가드레일 코드 전체가 `kind==='same'`인지만 본다. 3단계로 늘리면 그 코드를 전부 다시 봐야 하고, 실수로 `same_brand`가 판정에 섞여 들어갈 위험이 커진다. `relation`을 얹는 쪽이 가드레일을 원래대로 둔 채 세분화할 수 있었다 |

**받아들인 대가** — 입력 UI가 세 곳(AddPostModal·PurchaseLinkModal·EndedFillRow)에 중복돼 있다(기존에도 그랬다). `RelationPicker`는 admin/page.tsx 안에서만 공유하고 AddPostModal(다른 파일)은 같은 로직을 따로 구현했다 — 컴포넌트 하나를 3개 파일이 공유하게 뽑는 리팩터는 지금 범위를 넘는다고 판단했다.

**당시 확신도** — 높음. `note` 노출 사고는 실제 라이브 페이지에서 직접 확인했다(곰탕 공구, "브랜드가 달라요" 노출 재현).

## D-042 · 품절 감지가 페이지 앞부분만 보다가 실제 품절 배지를 놓치고 있었다 · 2026-08-25

**상태:** 유효

**상황** — 사장님이 "락앤락 데켓 IH 쿡플레이트", "Frh 컵라면도자기" 등이 실제로는 구매 버튼에 품절/sold out이 떠 있는데 우리 사이트엔 계속 진행 중으로 나온다고 짚어줬다. 확인해보니 `check_links.py`가 `r.text[:20000]`으로 페이지 앞부분만 봤는데, 두 몰 다 옵션 목록이 길어 실제 품절 표시가 7~8만자 지점에 있었다. 겸사겸사 카페24류 몰은 구매 버튼 라벨이 `<span class="butn-soldout">품절</span>`처럼 "품절" 두 글자뿐이라, 기존 문구 목록(`품절되었습니다`·`현재 품절` 등 긴 문구)에도 원래부터 안 걸렸다는 것도 발견했다.

**결정** — ① 페이지 전체를 본다(문자열 검색 비용은 무시할 만하다). ② "품절" 두 글자만 태그 안에 딱 박혀 있을 때만(`>품절<`, `alt="품절"`) 새 패턴으로 잡는다. 다시 돌려보니 이전엔 0건이던 품절 감지가 16건으로 늘었다(사장님이 짚어준 2건 포함) — 대부분 카페24 몰(Frh 등)이었다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| "품절" 두 글자를 문장 어디서나 매칭 | 실제로 시험해보니 "배송 지연 및 품절이 발생할 수 있습니다" 같은 안내 문구에도 걸려서 살아있는 공구를 잘못 숨길 뻔했다. 태그 안에 정확히 이 두 글자만 있을 때로 좁혔다 |
| 20000자 제한을 유지하고 더 넓히기만(예: 50000자) | 이번 두 사례가 각각 7만·8.8만자 지점이라 임의로 넓혀도 다음에 또 놓칠 수 있다. 페이지 전체를 보는 게 근본적인 해결이다 |

**받아들인 대가** — 매 점검마다 받는 페이지 크기가 커져서(20000자→전체, 최대 20만자 안팎) 약간 느려질 수 있다. 125건 기준 실행 시간 차이는 미미했다.

**당시 확신도** — 높음. 사장님이 짚어준 실제 두 사례로 재현·검증했고, 서버에서 다시 돌려 16건이 새로 잡히는 것도 확인했다.

**재검토 조건** — "품절" 태그 패턴이 다른 몰에서 오탐(멀쩡한 공구를 잘못 숨김)을 내면 패턴을 더 좁히거나 뺀다.

## D-041 · "오픈예정"·"상시딜"도 전용 페이지로 뺀다 · 2026-08-25

**상태:** 유효

**상황** — "카테고리를 누르면 오픈예정·상시딜은 상세페이지로 안 넘어간다"는 지적을 받았다. 실제 카테고리(유아동 등)는 `/category/[cat]` 전용 페이지로 이동하는 `Link`인데, 오픈예정·상시딜은 처음부터 "대응하는 페이지가 없어 홈에서 거르는 방식"(주석에 그렇게 적혀 있었다)이라 `<button>`으로 제자리 필터링만 했다 — URL도 안 바뀌고 눌러도 페이지가 안 넘어가니 "반응이 없다"고 느껴진 게 당연했다. 같은 자리에서 "넘어갈 때 뚝뚝 끊긴다"는 지적도 받았다 — 실제 카테고리끼리 이동해도 매번 헤더·본문이 통째로 새로 그려지며 흰 화면이 잠깐 번쩍였다.

**결정** — `/upcoming`(곧 열려요)·`/evergreen`(상시딜) 페이지를 새로 만들어 실제 카테고리와 똑같은 구조(`DealListClient`/`LandingPage`, JSON-LD, 사이트맵 자동 포함)를 태운다. `CategoryFilter`의 두 버튼을 `Link`로 바꾼다. 페이지 전환의 "뚝뚝 끊김"은 `app/template.tsx`(살짝 페이드인)와 `app/loading.tsx`(스피너)로 완화한다 — Next 14는 View Transitions API를 안 쓰므로 이 정도가 저비용으로 할 수 있는 선이다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 그대로 두고 홈 안에서만 필터링 | 사용자가 이미 "안 넘어간다"고 명확히 지적했다. 검색엔진 색인·공유·뒤로가기가 안 되는 것도 실제 카테고리와 차별이었다 |
| 헤드리스 애니메이션 라이브러리(Framer Motion 등) 도입 | "하지 않기로 한 것" — 외부 도구 도입 남발 대신, CSS 애니메이션 하나로 충분한 문제였다 |

**받아들인 대가** — 홈의 `currentCat` 상태에서 `'evergreen'`·`'upcoming'` 분기가 죽은 코드가 돼서 지웠다. `isEvergreen`/`getPeriodState`도 그 자리에선 더 이상 안 써서 import에서 뺐다.

**당시 확신도** — 높음. 로컬에서 직접 클릭해 이동·데이터 확인, 빌드 통과 확인.

## D-040 · 링크허브(tuk.link·linkon.id)는 자동 수집을 포기하고 수동 등록만 남긴다 · 2026-08-25

**상태:** 유효

**상황** — 관리자에서 인포크가 아닌 소스 4개(`link.theergo.co.kr/ig`, `bombom.tuk.link`(중복 등록 2건), `linkon.id/Danmom_shinhye`)를 어떻게 할지 물어보다가 하나씩 확인했다.

1. `theergo`는 페이지에 `utm_campaign=theergo`·`inpock_link` 흔적이 있어 확인해보니 `link.inpock.co.kr/theergo`가 그대로 열렸다 — **커스텀 도메인을 쓰는 인포크 계정**이었다. `source_type`만 `inpock`으로 바로잡고 실제 수집을 걸어보니 신규 후보 2건이 정상 수집됐다.
2. `tuk.link`·`linkon.id`(linkon.id는 "링크셀러"라는 별도 플랫폼)는 처음엔 정적 HTML이라 오판해서 기존 범용 수집기(`collect_linkhub`, 페이지의 `<a href>`를 그대로 뽑아 수동 검수용으로 로그만 남기는 함수)에 연결했는데, 서버에서 `BeautifulSoup`으로 다시 확인하니 실제 링크가 **0개**였다. 두 사이트 다 자바스크립트가 내용을 그리는 SPA라 단순 HTTP 요청으로는 빈 껍데기만 온다 — 처음 확인할 때 파비콘·메타태그의 `href=` 속성까지 세어버려 "정적이다"라고 잘못 판단했었다(원칙 2 위반, 정정함).
3. 겸사겸사 `collect_linkhub()`가 실제로는 `bs4`(BeautifulSoup) 없이 동작한 적이 한 번도 없었다는 것도 발견했다 — `requirements.txt`에 `beautifulsoup4`가 아예 없어서 이 경로를 타는 소스가 생기자마자 `No module named 'bs4'`로 조용히 실패하고 있었다.

**결정** — SPA 렌더링이 필요한 사이트를 위해 헤드리스 브라우저(Playwright 등)를 새로 들이지 않는다. 계정 2개 때문에 들이기엔 엔진 유지비가 너무 크고, "사이트별 크롤러를 새로 만들지 않는다"는 기존 방침과도 어긋난다. `tuk.link`·`linkon.id` 두 계정은 이름·인스타 핸들만 등록해 두고 새 공구는 사장님이 발견할 때마다 수동으로 넣는다. `bombom.tuk.link` 중복 등록 2건은 하나로 합쳤다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| Playwright 등 헤드리스 브라우저 수집기 추가 | 계정 2개를 위해 브라우저 엔진 전체를 서버에 들이는 건 유지비가 이득보다 훨씬 크다. 나중에 SPA 링크허브 계정이 여럿 생기면 그때 재검토 |
| `collect_linkhub`를 계속 시도만 시켜둠 | "0개 발견"만 매번 찍혀 수동 검수 후보 역할을 전혀 못 한다 — 차라리 수동임을 명확히 하는 게 낫다 |

**받아들인 대가** — `beautifulsoup4`를 추가해 `collect_linkhub` 자체는 정상 동작하게 됐지만(실제 정적 링크허브가 나오면 그때 도움이 된다), 지금 등록된 두 계정에는 당장 도움이 안 된다.

**당시 확신도** — theergo는 실제 수집 성공으로 검증. tuk.link/linkon.id의 "0개"는 서버에서 `BeautifulSoup`으로 직접 재현해 확인했다.

**상태:** 유효

다만 코드를 다시 보니 **내일(8/25)부터가 진짜 문제였다.** 관리자의 "오픈예정" 탭 개수·필터·배지가 전부 `p.status === 'upcoming'`이라는 저장값만 본다. `status`는 실제로 수집되기 전까지 절대 안 바뀌므로(`D-036`), 오픈일이 지나도 재수집이 안 되면 이 탭·배지는 **영영 "오픈예정"이라고 우긴다** — 심지어 날짜 텍스트(`periodLabel`)는 이미 지난 날짜(`8.24 오픈 예정`)를 그대로 보여줘서, 지나간 날짜에 "예정"이라고 붙는 모순된 표시가 된다. 같은 파일에 `공개됨`/`마감됨`을 `isExpired()`로 다시 가르는 선례(`isPublishedLive`/`isPublishedExpired`)가 이미 있는데, "오픈예정"만 그 패턴을 안 따르고 있었다.

**결정** — `isUpcomingOpen`/`isUpcomingOverdue` 두 함수를 추가해 `getPeriodState(p).kind`(날짜 기준)로 다시 가른다. "오픈예정" 탭은 진짜 아직 안 열린 것만 세고, 오픈일이 지났는데 여전히 미수집인 건 새 탭 "오픈일 지남 · 미수집"(빨간색, 0건이면 자동으로 숨김)으로 분리한다. 행 배지도 같은 기준으로 "오픈 예정"과 "오픈일 지남 · 미수집"을 나눈다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 오픈일이 지나면 `status`를 자동으로 뭔가로 바꿔주는 배치 작업 추가 | 이미 `D-037`에서 고객 화면은 날짜로 다시 계산하도록 고쳐서, 저장값을 굳이 건드릴 필요가 없다. `status`를 함부로 바꾸는 코드가 늘면 `inpock.py`의 재수집 매칭(`status='upcoming'` 전제)과 충돌할 위험이 더 크다 |
| 오늘 하루도 "오픈일 지남"으로 앞당겨 표시 | 오픈 당일은 아직 정상적으로 기다리는 중이다(수집기가 하루 2회 돈다) — 미리 경고하면 사장님이 매일 오픈 당일마다 헛걸음할 판단을 하게 된다 |

**받아들인 대가** — 없음. 고객 화면과 완전히 같은 `getPeriodState`를 재사용했을 뿐이라 새 판단 기준이 생기지 않았다.

**당시 확신도** — 높음. `isPublishedLive`/`isPublishedExpired`와 동일한 패턴이라 검증이 쉬웠고, 로컬 빌드로 확인했다.

## D-037 · 가격 없는 자리표시자는 오픈일이 지나도 일반 목록에 안 보여준다 · 2026-08-24

## D-034 · 날짜 경계를 서버 시간(UTC)이 아니라 KST로 통일한다 · 2026-08-25

**상태:** 유효

**상황** — "오늘 오픈 날짜가 맞는지" 확인하다가, `lib/period.ts`의 `daysLeft()`가 `new Date()`를 서버 로컬 자정 기준으로 쓰고 있었다는 걸 발견했다. 서버 타임존은 `Etc/UTC`다. 한국은 UTC+9라서 **UTC 15:00~23:59(KST 00:00~08:59, 한국 새벽)** 9시간 동안은 KST 날짜가 UTC 날짜보다 하루 앞선다. 그 구간엔 "오늘 오픈"·D-day·마감 판정·`isCustomerVisible()`의 마감일 비교가 전부 하루 밀려 있었다.

우연한 버그가 아니라 **매일 정해진 시각에 실제로 걸리는 버그**였다. `check_links.py`는 cron이 `KST 05:00`(주석에 그렇게 적혀 있다 — 실제로는 `0 20 * * *` = UTC 20:00)에 도는데, UTC 20:00은 정확히 위 드리프트 구간 안이다. 즉 이 스크립트는 **돌 때마다 항상 하루 늦은 날짜로 판정**하고 있었다.

`lib/landing.ts`의 `kstToday()`는 이미 이 문제를 알고 KST로 보정한 값을 썼다(`D-016` 즈음부터). `period.ts`만 그 패턴을 안 따라갔다.

**결정**

1. `kstNow()`/`kstToday()`를 `lib/kst.ts`로 뺀다. `period.ts`가 `landing.ts`를 import하면 순환 참조가 생겨서(`landing.ts`가 이미 `period.ts`를 쓴다) 별도 파일이 필요했다 — `SITE_URL`을 `lib/siteUrl.ts`로 뺀 것과 같은 이유다.
2. `daysLeft()`와 `isCustomerVisible()`의 인라인 마감일 비교를 `kstToday()` 기준으로 고친다.
3. `check_links.py`에 `kst_today()`를 같은 계산으로 추가하고 `date.today()` 두 곳을 바꾼다.
4. **파이썬 나머지(`inpock.py`, `scraper.py`, `scripts/*.js`)는 이번에 안 고친다** — 아래 참고.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 서버 시스템 타임존을 `Asia/Seoul`로 바꿈 | EC2 인스턴스 설정을 건드리는 일이라 되돌리기가 상대적으로 무겁고, 다른 서비스(로그·cron 시각 표기)에도 영향을 준다. 코드에서 명시적으로 KST를 계산하는 편이 더 좁고 안전한 변경이다 |
| 발견한 모든 `date.today()`/로컬 Date 사용을 한 번에 다 고침 | `inpock.py`(가격·마감일 파싱 여러 곳), `scraper.py`, `lib/analytics.ts`(일별 집계 버킷), `scripts/cleanup-lapsed-upcoming.js`/`publish-upcoming.js`(수동 실행 스크립트)에도 같은 패턴이 있다. 전부 한 번에 고치면 검증 범위가 너무 커진다. 지금 고친 두 곳(`period.ts`, `check_links.py`)은 고객 화면에 직접 보이거나 매일 정해진 시각에 확정적으로 버그가 걸리는 곳이라 우선순위가 확실했다 |

**받아들인 대가** — `lib/analytics.ts`의 `recordEvent()`가 여전히 `new Date().toISOString().split('T')[0]`(UTC)로 날짜 버킷을 나눈다. 그 9시간 구간에 발생한 이벤트는 관리자 통계에서 KST 기준 하루 전 날짜에 잡힌다 ⚠️. `inpock.py`의 마감일 파싱(`_parse_deadline_candidate` 등)도 같은 위험이 있다.

**당시 확신도** — `period.ts`/`check_links.py` 수정은 높음(시뮬레이션으로 드리프트 구간 전후 값을 직접 확인했고, 지금 이 순간 Python `kst_today()`와 Node `kstToday()`가 일치하는 것도 확인했다). 나머지 안 고친 곳들의 영향 범위는 낮은 확신 ⚠️ — 실제로 얼마나 자주 문제가 되는지는 안 재봤다.

**재검토 조건** — `lib/analytics.ts`의 일별 통계가 눈에 띄게 이상해 보이면(예: 특정 날짜만 방문자가 비정상적으로 적거나 많음) 그때 `recordEvent()`를 고친다. `inpock.py`의 마감일이 실제로 하루 어긋난 사례가 나오면 그때 고친다.

## D-036 · 오픈 예정 자리표시자가 정식 공구로 바뀐 뒤에도 안 내려가던 버그 · 2026-08-25

**상태:** 유효

**상황** — "오늘 오픈한 게 관리자에서 공개됨으로 바뀌었는지" 확인하다가 두 가지를 발견했다.

| 대안 | 버린 이유 |
|---|---|
| 지금 중복된 두 게시물만 수동으로 정리 | 원인 코드를 안 고치면 다음에 오픈하는 예정 공구마다 계속 반복된다. 오늘만 5건 중 1건이 이미 걸렸다 |

**받아들인 대가** — 이미 이 상태로 쌓인 다른 자리표시자가 있을 수 있다(오늘 이전에 오픈해서 정식 수집됐는데 예고가 안 지워진 것). 이번엔 오늘 발견한 1건만 재수집으로 바로 정리했고, 과거분을 전수 조사하지는 않았다 ⚠️.

**당시 확신도** — 원인은 코드로 직접 확인해 높음. 다만 자리표시자에 정식 가격·이미지·구매링크가 어떻게 채워져 있었는지는 코드 경로를 다 뒤져도 못 찾았다 ⚠️ — `inpock.py` 어디에도 기존 게시물의 `price`/`img`/`purchase_url`을 그 자리에서 고치는 코드가 없다. 관리자가 직접 수정했을 가능성이 있다.

**재검토 조건** — 과거분도 확인했다(2026-08-25). `status='upcoming'`이면서 가격이 채워진 게시물은 이 1건뿐이었다 — 오래 곪은 문제가 아니라 `D-029`가 배포된 뒤 처음 걸린 사례였다.

## D-035 · "오늘의 공구"에서 아직 안 열린 예고를 뺀다 · 2026-08-25

**상태:** 유효 (`D-029`가 만든 `todayPosts()` 세 번째 조건을 대체)

**상황** — 오늘 오픈 예정 5건 중 실제로 열린 건 확인해 보니 1건(루엔 회전책장, 228,000원)뿐이었고 나머지 4건은 여전히 가격·이미지·링크가 없었다. 그런데 `D-029`에서 만든 `todayPosts()`는 "오늘 오픈 예정"이면 내용이 비어 있어도 무조건 "오늘의 공구"에 넣고 있었다 — 방금 채워진 진짜 공구 옆에 "가격 미정" 빈 카드가 나란히 떴다.

**결정** — 오늘 오픈 예정인데 아직 가격이 없으면(`getPeriodState().kind === 'upcoming' && !price`) "오늘의 공구"에서 뺀다. 대신 "곧 열려요"에만 있는다. `upcomingPosts()`도 같은 기준으로 가격이 채워진 건 빼서, 같은 공구가 두 영역에 동시에 뜨는 일이 없게 했다.

기준은 `status` 필드가 아니라 **가격 유무**다. `status`는 수집기가 실제 내용을 채워 넣어도 아무도 안 바꿔서 그대로 `'upcoming'`으로 남는다 — 루엔 회전책장도 가격이 들어온 뒤에도 `status: 'upcoming'`이었다. `status`만 보고 걸렀으면 방금 열린 진짜 공구까지 걸러낼 뻔했다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `status`가 `'upcoming'`이면 무조건 제외 | 실제로 데이터가 채워진 것(루엔 회전책장)까지 걸러낸다. `status`는 수집기가 안 바꾸는 필드라 신뢰할 수 없다 |
| 수집기가 실제 데이터를 채우면 `status`도 함께 바꾸게 함 | 맞는 방향이지만 파이썬 수집기 로직을 고치는 더 큰 변경이다. 지금은 프런트에서 가격 유무로 우회하는 게 더 좁고 안전하다 |

**받아들인 대가** — `status`가 여전히 부정확하다. 관리자 화면에서 "오픈 예정" 필터로 이 공구를 찾으면 여전히 나온다(가격이 있는데도). 근본 수정은 수집기가 데이터를 채울 때 `status`를 `needs_review`나 `ready`로 바꾸는 것인데, 이번엔 안 했다.

**재검토 조건** — 오늘 오픈 예정 중 실제로 열리는 비율(1/5, 20%)이 계속 이 정도로 낮으면, 수집기가 예고 블록을 실제 판매 페이지에 매칭하는 로직 자체를 다시 봐야 한다.

## D-033 · 제휴 문의 창구를 만든다 — 저장이 이메일보다 먼저다 · 2026-08-25

**상태:** 유효

**상황** — 인플루언서·브랜드가 "우리 공구도 올려주세요" "제휴하고 싶어요"라고 생각해도 연락할 곳이 없었다. `/request`(공구 등록 요청)는 이미 있었지만 구매 링크·가격이 필수라 "이 공구 하나를 등록해 주세요"용이다. 아직 판매 페이지가 없는 제휴 제안(브랜드가 "이런 상품이 있는데 공구해 볼래요?")은 못 받는다.

**결정** — `/propose` 페이지(전 페이지 하단 링크, 관리자 화면 제외)를 만들고 `/api/inquiries`로 받는다.

1. 필드: 구분(인플루언서/브랜드/업체) · 이름 · 연락처 · 인스타그램·사이트(선택) · 공구 상품(선택) · 제안 내용.
2. **저장이 이메일 발송보다 먼저다.** `data/inquiries.json`에 항상 저장한 뒤 SMTP가 설정돼 있으면 메일도 보낸다. 메일 서버가 죽어도(또는 애초에 설정을 안 했어도) 문의는 안 사라진다 — `emailed: false`로 표시만 되고, 관리자 「제휴 문의」 탭이 최종 백업이다.
3. `/request`와 같은 허니팟 패턴(숨은 `website` 필드)으로 스팸을 거른다.
4. `/api/inquiries`는 POST만 공개, GET·PATCH는 관리자 전용 — `middleware.ts`의 `isProtected()`와 `matcher` 양쪽에 등록했다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `/request`에 필드만 추가해서 재사용 | 그 창구는 서버가 구매 링크·가격을 강제하는 전제로 짜여 있다(`enforcePurchaseLinkRequirement`와는 별개지만 폼 자체가 그 전제다). 제휴 제안은 상품이 아직 안 정해졌을 수도 있어 성격이 다르다 |
| 이메일만 보내고 서버에 안 남김 | SMTP 계정을 지금 갖고 있지 않다(사장님이 설정해야 한다). 설정 전에 들어온 문의를 놓치면 안 되고, 설정 후에도 메일 서버 장애로 놓칠 수 있다 |
| mailto: 링크로 대체 | 문의 내용이 구조화되지 않고, 발신자의 메일 앱 설정에 기대야 한다. 서버에 기록도 안 남는다 |
| 헤더 아이콘 줄에 추가 | 이미 붐빈다(찜·팔로우·알림·등록요청·인플루언서목록 5개). 사장님이 "상단이나 푸터에 하나만"이라고 특정했고, 이 창구는 고객의 매일 쓰는 동작이 아니라 가끔 오는 업무 문의라 우선순위를 낮게 뒀다 |
| 문의 상태를 여러 단계(접수/검토중/완료)로 관리 | 처리/미처리 두 상태면 충분하다. 지금 규모(하루 수 건 이하로 예상)에 단계를 나누면 관리 비용이 더 크다 |

**받아들인 대가** — SMTP 계정이 설정되기 전까지는 메일이 전혀 안 나간다. 관리자가 「제휴 문의」 탭을 직접 열어봐야 안다 — 아직 배지(탭 라벨의 미처리 건수)만 있고 별도 알림은 없다.

**당시 확신도** — 폼·저장·보호는 높음(로컬에서 실제 제출·조회·인증 차단을 확인했다). 메일 발송은 사장님이 SMTP 계정(네이버 메일 앱 비밀번호 등)을 주기 전까지 미검증이다 ⚠️.

**재검토 조건** — 문의가 하루 여러 건 들어오기 시작하면 상태를 3단계로 늘리는 걸 재고한다. 메일이 계속 실패하면(제공사 정책 등) SMTP 대신 Resend 같은 API 방식으로 바꾼다.

## D-032 · 관리자 첫 화면을 "몇 명 들어왔지?"에서 "오늘 뭘 손보면 돈이 될까?"로 바꾼다 · 2026-08-25

**상태:** 유효 (`D-020`/`D-025`의 상단 배너를 대체)

**상황** — 사장님이 외부에서 받은 조언을 그대로 전달했다: 관리자 첫 화면이 "공개 72 · 판정 가능 47 · 대기 1091 · 오늘 방문자 29명"처럼 상태 개수부터 보여주는데, 보고 나서 뭘 해야 할지가 안 나온다는 지적이었다. 첫 화면의 질문을 "몇 명 들어왔지?"에서 "오늘 어떤 상품을 손보면 돈이 될까?"로 바꾸자는 제안이었고, 타당했다.

**결정** — 상단 통계 카드(공개됨/공개 가능/검수 필요/공구 후보)와 `D-025`의 backlog 배너를 지우고, `TodayPriorities` 컴포넌트로 바꿨다.

1. 최근 14일 퍼널: 검색 유입 → 상세 조회 → 구매처 클릭. 비율 포함.
2. 우선순위 세 묶음 — 전부 이미 있는 집계(`postSources`·`detailViews`·`clickBreakdown`)를 다르게 자른 것뿐이다.
   - 🔥 검색 유입 있는데 비교가 없는 상품 → 「채우기」로
   - 💰 조회수 있는데 구매 링크가 없는 상품 → 「수익화 현황」으로
   - ⚠️ 종료됐는데 대체 상품도 없는 상품 → 「채우기」로
3. 각 묶음은 상위 3건 제목+지표를 미리 보여주고 "목록으로 →"로 해당 탭으로 이동한다.

「데이터」 탭에도 개별 로그 위에 요약 3숫자(검색 유입 · 검색→상세 · 상세→구매처클릭)를 추가했다 — 개별 로그(최근 300건, 대략 일주일치)만으로 계산한 비율은 표본이 작아 출렁이므로, 14일 집계에서 낸다.

**뺀 것 두 가지 — 조언에는 있었지만 만들지 않았다**

- **예상 수익.** 클릭까지는 알지만 결제 여부를 모른다. 파트너스 클릭이 실제 구매로 이어졌는지는 쿠팡·네이버 파트너스 자체 대시보드에서만 확인된다. `analytics.json`에 결제·전환 데이터가 전혀 없다 — 없는 숫자를 지어내면 원칙 1(틀린 숫자를 내보내는가)을 정면으로 어긴다.
- **검색 급상승 상품.** 상품별 유입 경로(`postSources`)가 쌓인 지 사흘뿐이다(2026-08-22 시작). 이번 주 대비 지난주를 비교하려면 최소 2주치가 있어야 한다. 자리는 만들어 두고("데이터가 더 쌓이면 여기 보여요") 비활성 상태로 둔다 — 데이터가 없는데 "+82%"를 보여주면 그게 원칙 1 위반이다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 상태 개수 카드를 유지하면서 우선순위만 추가 | 첫 화면의 "질문"을 바꾸자는 게 요청의 핵심이다. 카드를 남기면 여전히 개수가 먼저 보인다. 공개·검수·후보 개수는 「공구 관리」 탭 필터 칩에 그대로 남아 있어 실제로는 안 사라졌다 |
| "검색→상세" 비율을 `detailViews`(전체 조회수) 기준으로 계산 | 실측하니 371/266=139%가 나왔다. 검색 유입은 방문(세션) 수, 상세조회는 클릭(이벤트) 수라 한 사람이 여러 상품을 보면 분모보다 분자가 커진다. `postSources`의 검색 발생분(128건)으로 분자를 맞추니 48%로 앞뒤가 맞았다 |
| 예상 수익을 "쿠팡 평균 수수료율 × 클릭수"로 추정 | 클릭이 결제로 이어질 확률도, 실제 수수료율도 우리가 모른다. 두 겹의 추정을 곱해 "수익"이라고 표시하면 숫자처럼 보이는 억측이다 |
| 개별 방문 로그를 아예 다른 메뉴로 옮김 | 이미 「데이터」 탭으로 분리돼 있었다(`D-023`대 작업). 요약만 그 탭 위에 추가했다 |

**받아들인 대가** — `D-025`가 만든 "판정 없이 쌓인 공구" 경고 문구(고객 화면 기준 카운트)가 사라졌다. 우선순위 묶음 🔥가 그 자리를 대신하지만 기준이 다르다 — `D-025`는 "판정 없이 보이는 공구 전체"를, 새 기준은 "그중 검색 유입이 있는 것"만 센다. 검색 유입이 없는데 판정만 빈 공구는 이제 첫 화면에서 안 보인다(대신 「채우기」 탭에는 여전히 다 있다).

**당시 확신도** — 높음. 세 묶음 모두 실측 데이터로 결과를 확인했다(예: 💰 45건, ⚠️ 25건, 상위 항목이 매파빌·미쁨곰탕처럼 이미 알려진 우선순위와 일치).

**재검토 조건** — `postSources`가 2주 이상 쌓이면 급상승 위젯을 켠다. 실제 구매 데이터를 얻을 방법(쿠팡 파트너스 리포트 연동 등)이 생기면 예상 수익을 다시 검토한다.

## D-031 · 대체 상품 화면을 예상보다 일찍 붙인다 — 실제 신호가 나왔다 · 2026-08-25

**상태:** 유효 (`D-030`의 "구조만 만들고 화면은 나중에" 부분을 부분적으로 뒤집음)

**상황** — `D-030`은 "비교불가 사유에 `not_found`가 쌓이면 그때 화면을 붙인다"고 재검토 조건을 걸어 뒀다. 그런데 그 신호가 카운터가 아니라 **사장님이 직접 채우기 작업을 하다가 막히는 것**으로 먼저 왔다 — "매파빌 르베르360 이런거 파트너스 링크가 없어서 ㅠㅠ".

두 상품을 확인해 보니:
- 오르다 매쓰파워빌더스 〈매파빌〉(188,000원, 브랜드 "오르다") — 조회 1위(18회)
- 르베르360유모카(298,000원, 브랜드 "르베르360유모카") — 조회 2위(10회)

둘 다 니치 브랜드의 고가 상품이라 쿠팡 파트너스에 동일 상품 자체가 없을 개연성이 높다. `compare_none_reason`의 `not_found`는 **판정용 비교가**를 못 찾을 때 쓰는 필드라 이 상황(종료 공구의 **동일 상품 구매 링크**를 못 찾음)과는 다른 필드였다 — 신호를 잡을 자리가 원래 없었다.

**결정** — `D-030`에서 만들어 둔 `kind: 'same' | 'alternative'` 구조를 그대로 써서 화면을 붙인다. 예상보다 일찍 붙이는 이유는 카운터를 기다릴 필요 없이 **최우선 순위 상품 2건에서 바로 막혔기 때문**이다 — 이건 이미 충분한 신호다.

1. `EndedFillRow`(채우기 「종료·링크없음」)에 접이식 "똑같은 상품을 못 찾았을 때 — 비슷한 상품" 칸을 추가. 기본은 접혀 있다 — 동일 상품 링크가 있으면 볼 일이 없는 칸이다.
2. `EndedDealNotice`가 링크를 `same`/`alternative`로 나눠 다르게 그린다. `same`이 있으면 그것만 "구매하기"로. 없고 `alternative`만 있으면 문구를 분명히 갈라 보여준다: *"똑같은 상품은 찾지 못했어요. 대신 비슷한 용도로 지금 살 수 있는 상품이에요."* + *"※ 이 공구와 같은 상품이 아니라서 저희가 가격을 비교하지 않았어요."*
3. `BetterPriceNotice`(아쉽딜)는 `sameProductLinks()`만 받는다 — 다른 상품 가격을 "더 싸다"고 말하는 건 판단 기준 1번을 정면으로 어긴다.
4. `hasPurchaseLink()`는 그대로 `same`만 센다. `alternative`만 채운 공구도 「종료·링크없음」 작업 목록에 **계속 남는다** — 진짜 동일 상품을 찾으면 언제든 대체할 수 있게. 다만 행 머리에 "대체 상품 안내 중" 배지를 달아 다시 열어보지 않아도 상태를 안다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `not_found` 카운터가 쌓이길 계속 기다림 | 최우선 순위 2건이 이미 막혀 있다. 카운터를 기다리는 동안 조회 28회(18+10)가 계속 샌다 |
| `alternative` 링크도 `hasPurchaseLink`에 포함 | 작업 목록에서 사라지면 관리자가 나중에 진짜 동일 상품이 나와도 다시 찾을 이유가 없어진다. 대체는 임시 조치다 |
| 「구매하기」 문구를 그대로 씀 | 다른 상품을 같은 상품인 것처럼 판다. 신뢰가 걸린 문제라 문구를 반드시 갈라야 한다 |
| RevenueBoard의 빠른 입력창(`PurchaseLinkModal`)에도 대체 상품 칸 추가 | 그 창은 "동일 상품을 빨리 넣는" 자리로 설계됐다. 대체 상품은 검색을 충분히 시도한 뒤에 쓰는 것이라 「종료·링크없음」 탭의 느린 흐름에 더 맞는다 |

**받아들인 대가** — `D-030`이 걸어 둔 "카운터가 쌓일 때까지 기다린다"는 조건을 지키지 못했다. 대신 근거는 더 확실하다 — 추상적 숫자가 아니라 최우선 순위 실물 2건이다.

**당시 확신도** — 높음. 판정 오염 가드는 `D-030`에서 이미 검증됐고, 이번엔 화면 렌더까지 로컬에서 직접 확인했다(대체 상품만 있는 마감 공구에 정확한 문구가 뜨는 것).

**재검토 조건** — 대체 상품 링크의 클릭이 실제로 발생하는지 「데이터」 탭에서 지켜본다. 전혀 안 눌리면 이 기능은 있으나 마나 한 것이다.

## D-030 · 대체 상품 추천은 구조만 만들고 화면은 나중에 붙인다 · 2026-08-24

**상태:** → `D-031`로 뒤집힘 (입력칸·화면을 실제로 붙였다)

**상황** — "마감돼서 구하기 힘들거나 공구가 비쌀 때, 비슷한 용도의 더 싼 상품을 권하면 어떨까"는 제안이 나왔다. 고객 입장에서 정당한 제안이다 — 못 사는 걸 알고 나면 "그럼 뭘 사지"가 다음 질문이다.

다만 지금 만들 일은 아니다. **동일 상품 제휴 링크가 아직 20건**이고 조회 상위 10건도 안 채워졌으며 제휴 클릭은 0회다. 대체 상품 링크도 사람이 하나씩 만들어야 해서 일이 두 배가 된다. 그리고 그 자리를 이미 부분적으로 채우는 게 있다 — 마감 공구의 「이런 건 어때요?」가 **우리 공구**를 권한다(`D-023`의 제목 매칭). 우리 공구는 판정이 붙어 있고 유입도 우리 것이다.

**결정** — 구조만 만든다.

1. `PurchaseLink.kind: 'same' | 'alternative'`. 값이 없으면 `same` — 기존 데이터는 마이그레이션 없이 그대로다.
2. **`getDealVerdict()`는 `same`만 비교가로 쓴다.** 다른 상품 가격으로 할인율을 내면 화면에 틀린 숫자가 나간다 — 판단 기준 1번이다.
3. `hasPurchaseLink()`도 `same`만 센다. "공구는 끝났지만 지금 살 수 있어요"에 다른 상품이 뜨면 그 문장이 거짓이 된다.
4. 입력칸과 고객 화면은 만들지 않는다.

**화면을 붙일 때 지킬 것** (거부감이 생기는 자리를 미리 적어 둔다)

| | 거부감이 생길 때 | 안 생길 때 |
|---|---|---|
| 시점 | 살 수 있는데 다른 걸 권함 | 이미 "못 산다"를 안 뒤 (마감·아쉽딜) |
| 관련성 | 곰탕 → 세이펜 | 곰탕 → 다른 곰탕 |
| 동기 | 왜 보여주는지 모름 | 이유가 문구에 있음 |

- 진행 중 꿀딜엔 **절대 안 붙인다.** "제일 싸다"고 판정해 놓고 다른 걸 권하면 판정기가 아니라 쇼핑몰이 된다(`D-027`과 같은 이유).
- 문구가 이유를 말해야 한다. "이 상품 어때요?"는 광고로 읽힌다 → "공구는 끝났지만, 같은 용도로 지금 살 수 있는 것".
- **판정이 없다는 걸 밝힌다** — "이 상품은 저희가 가격을 따로 판정하지 않았어요". 판정된 것과 소개하는 것이 섞이면 신뢰가 무너진다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 지금 화면까지 다 만듦 | 채울 사람이 없다. 동일 상품 링크가 20건인데 대체까지 하면 일이 두 배다 |
| 별도 필드(`alternative_links[]`)로 분리 | 저장·정규화·표시가 두 벌이 된다. `purchase_links` 하나에 `kind`만 붙이면 기존 경로를 그대로 쓴다 |
| 자동으로 비슷한 상품을 찾아 붙임 | 우리에게 상품 카탈로그가 없다. 쿠팡 검색 링크는 파트너스 추적이 안 돼 수수료가 0이다(`c542b7a`) |
| 대체 상품도 비교가로 씀 | **절대 안 된다.** 다른 상품 가격으로 할인율을 내면 틀린 숫자가 나간다 |
| 구조도 안 만들고 나중에 통째로 | 나중에 붙이는 사람이 판정 오염을 모르고 지나칠 수 있다. 그 가드가 이 결정의 핵심이다 |

**받아들인 대가** — 쓰이지 않는 필드가 하나 늘었다. 입력칸이 없으므로 당분간 `alternative` 링크는 만들어질 수 없고, 가드도 실제로는 안 걸린다(모의로 검증만 했다).

**당시 확신도** — 가드는 높음(운영 데이터로 오염되지 않음을 확인했다). **화면을 만들 시점은 낮음** ⚠️

**재검토 조건** — 비교불가 사유에 `not_found`("검색해도 안 나옴")가 쌓이면 그때 화면을 붙인다. 지금은 0건이고, `exclusive` 4건 · `no_same_set` 2건이다 — `exclusive`는 원래 다른 데서 안 파는 상품이라 대체 추천이 어색하다.

## D-029 · 오픈 예정을 공개하고, 알림은 우리가 보내지 않고 캘린더에 맡긴다 · 2026-08-24

**상태:** 유효 (`todayPosts()`에 넣던 부분만 `D-035`로 뒤집힘)

**상황** — `status='upcoming'` 55건이 전부 `published=false`라 홈에도 상세에도 안 나왔다. 상세 조회가 **전 건 0회**였다. 인플루언서가 예고한 일정이 통째로 숨어 있던 것이다.

여기에 "알림받기"를 붙이자는 이야기가 나왔다. 그런데 우리가 가진 웹 푸시는 **구독자가 3주째 2명**이다. 구현 문제가 아니라 환경 제약이다 — iOS는 홈 화면에 추가해야만 되고, 네이버앱·인스타 인앱 브라우저는 Service Worker가 막힌다. 우리 방문의 상당수가 그 둘이다(7일 인앱 고유 IP: 네이버앱 128).

**결정**

1. 오픈 예정 공구를 공개하고, 홈에 **「곧 열려요」** 영역과 카테고리 필터를 둔다.
2. 알림은 **우리가 보내지 않는다.** 「캘린더에 담기」로 `.ics`를 내려주고, 알림은 고객 폰의 캘린더가 한다.
3. 일정은 **종일 일정**으로 만든다. 오픈 "시각"은 우리도 모른다.
4. 캘린더 링크에 `utm_source=calendar`를 붙이고 `TrafficSource`에 `calendar`를 더한다 — 이 기능이 실제로 사람을 데려오는지 재기 위해서다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 웹 푸시로 알림 | 방문자 대부분에게 **도달 자체가 안 된다.** 3주째 구독자 2명이 그 증거다. 도달 0인 채널로는 재방문도 브랜드도 못 만든다 |
| 카카오톡 채널 | 도달은 되지만 채널 개설·발송 정책·비용을 확인해야 한다 ⚠️. 캘린더는 오늘 만들 수 있다 |
| 이메일 | 주소 입력은 부담이 크다. 찜(탭 한 번)조차 31일간 0회였다 |
| 오픈 시각을 오전 10시로 가정 | 화면에 우리가 모르는 사실이 적힌다. 마감일을 모를 때 날짜를 만들지 않기로 한 것과 같다(`D-026`) |
| 알림 기능을 아예 안 만듦 | 실제로 제가 권한 안이었다 — 찜 0회, 오픈예정 조회 0회라 수요 증거가 없었다. **사장님이 만들기로 결정했다** |
| `utm_source=calendar`를 `external`로 뭉갬 | 효과를 못 잰다. 이 기능은 재방문을 만드는 게 목적이라 구분이 지표 그 자체다 |

**받아들인 대가**

- 공개하는 40건 남짓은 **제목·오픈일·인플루언서만 있다.** 가격·이미지·구매 링크가 없다(인포크 예고 블록이라 상품 페이지가 아직 없다). 얇은 페이지가 색인된다는 뜻이고, SEO에 불리할 수 있다 ⚠️
- 알림을 우리가 안 보내므로 **그 순간 우리 이름이 안 뜬다.** 캘린더 일정 제목에 "[꿀공구]"를 넣고 링크에 utm을 붙이는 것으로 대신한다
- 종일 일정이라 알림이 정확한 오픈 시각에 안 온다. `VALARM TRIGGER:PT9H`로 그날 아침에만 울린다

**당시 확신도** — 캘린더가 푸시보다 낫다는 건 높음(도달률이 근거다). **기능 자체의 수요는 낮음** ⚠️ — 찜 0회, 오픈예정 조회 0회에서 시작한다.

**재검토 조건** — 2주 뒤 `calendar` 유입이 0이면 이 기능은 수요가 없는 것이다. 그때는 오픈 예정 노출만 남기고 캘린더 버튼을 내린다.

## D-028 · 무중단 배포로 바꾼다 · 2026-08-24

**상태:** 유효 (`D-015`의 교체 방식을 대체)

**상황** — 빌드는 별도 디렉터리에서 하고 `.next`를 바꿔치웠지만, 마지막 `pm2 reload`가 fork 모드 단일 인스턴스라 사실상 재시작이었다. 그 1~2초 동안 nginx가 502를 냈고 로그에 **42건** 남아 있다. 하루 방문 80명이면 확률은 낮지만 0은 아니다.

**결정** — 슬롯 두 개를 번갈아 쓴다. `.next-a ↔ 3002` / `.next-b ↔ 3003`. 새 슬롯에 빌드해 새 포트로 띄우고, **살아난 걸 확인한 뒤에** nginx가 보는 포트를 바꾸고 reload한다(nginx reload는 graceful이라 진행 중인 요청도 안 끊긴다). 옛 인스턴스는 그다음에 내린다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| PM2 cluster 2 인스턴스 | **상시** 2개가 뜬다. 빌드와 겹치면 OOM 위험이 있다는 판단은 그대로 유효하다(스왑 0, 가용 820MB). blue/green은 빌드가 끝난 뒤에만 잠깐 겹친다 |
| 그냥 두기 | 무중단 이득이 작다고 봤는데, sudo가 무암호로 되고 메모리도 여유가 있어(인스턴스 169MB / 가용 820MB) 비용이 거의 없다 |
| nginx upstream + 헬스체크 자동 failover | 전환이 아니라 장애 대응이다. 배포 시점을 우리가 정하는 상황에는 과하다 |

**받아들인 대가**

- 배포 스크립트가 nginx 설정을 고친다. sudo가 필요하고, 설정이 깨지면 사이트가 죽는다 — `nginx -t`로 검사하고 실패하면 되돌린다.
- 전환 순간 두 인스턴스가 겹친다. 그동안 둘 다 `data/*.json`을 쓸 수 있고 `savePosts()`에 락이 없다(기술부채 #2). 수집 cron(09:00·14:00)과 겹치지 않게 배포하는 게 안전하다 ⚠️
- 서버 비용은 **안 바뀐다.** EC2는 시간당 고정이라 인스턴스가 잠깐 둘이어도 요금이 같다. 비용에 영향을 주는 건 배포 방식이 아니라 배포 횟수(빌드 CPU)다.

**당시 확신도** — 높음. 실패 시 nginx를 아예 안 건드리므로 예전 방식(교체한 뒤 되돌리기)보다 안전하다.

**재검토 조건** — 전환 중 데이터 유실이 실제로 관측되면 `savePosts()`에 락을 먼저 넣는다.

## D-027 · 수익화는 화면 개선이 아니라 링크 채우기부터 한다 · 2026-08-23

**상태:** 유효

**상황** — 개발 우선순위를 수익화 중심으로 옮기면서 상세 페이지 구매 영역을 판정별로 나누자는 요청이 나왔다(꿀딜엔 "비슷한 제품 보기", 아쉽딜엔 "가격대 비교", 종료엔 "현재 구매하기"). 방향은 맞지만 재보니 **붙일 링크가 없었다.**

- 제휴 링크 클릭: 전체 기간 **0회**
- 제휴 링크가 고객 화면에 뜨는 공구: **18건 / 2,358건**
- 반면 마감됐는데 살 곳을 못 알려주는 공구가 190건이고, 그중 **상위 10건이 조회의 86%**

화면을 아무리 잘 고쳐도 나머지 2,340건에서는 아무것도 안 바뀐다. 개선 효과를 잴 분모 자체가 없다.

**결정** — 순서를 이렇게 잡는다.

1. 「종료·링크없음」 상위 10건에 파트너스 링크를 채운다 (코드 없음)
2. 관리자 **수익화 현황** 표 + 「수익화 필요」 필터 — 어디에 붙여야 하는지를 숫자로 본다
3. 상세 조회에 유입 경로를 함께 기록한다(`postSources`) — 상품별 검색유입을 알 수 있게
4. 아쉽딜에 대체 구매처 노출 (판단 필요)

**보류** — 꿀딜의 "비슷한 제품 보기", 종료 화면의 "비슷한 제품 3개".

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 요청받은 순서대로 상세 화면 분기부터 | 링크가 18건뿐이라 대부분의 페이지에서 화면이 안 바뀐다. 효과를 측정할 수 없다 |
| 꿀딜에 "쿠팡에서 비슷한 제품 보기" | **"제일 싸다"고 판정해 놓고 다른 데로 보내는 모양**이 된다. 판정기라는 정체성과 부딪힌다 |
| "비슷한 제품"을 쿠팡 검색 링크로 | 파트너스 추적 링크가 안 만들어져 **수수료가 0이다**. 사장님이 `c542b7a`에서 이미 확인한 사실이다 |
| "비슷한 제품"을 상품마다 발급 | 동일 제품 링크에 더해 일이 두 배가 된다. 동일 제품도 아직 18건이다 |
| 아쉽딜 분기를 먼저 | 대상이 **5건**이다. 화면 분기를 하나 더 만들 값어치가 지금은 없다 |
| 검색유입을 `daily[날짜].sources`로 추정 | 방문 단위라 상품과 안 묶인다. 나눠 배분하면 지어낸 숫자가 된다 |
| 지난 기록을 소급 계산 | 원본에 상품·경로 짝이 없어서 불가능하다. 오늘부터 쌓는다고 화면에 적었다 |

**받아들인 대가**

- 상세 페이지 구매 영역은 이번에 안 바뀐다. 요청의 1-a·1-c는 미뤄졌다.
- 상품별 검색유입은 **소급이 안 된다.** 표에 열은 있지만 한동안 비어 보인다 — 없는 값을 있는 것처럼 채우지 않기로 했다.
- "수익화 필요" 판단에 마감/진행을 섞어 보여준다. 마감 공구가 먼저지만, 진행 중 공구도 사람이 보고 판단할 수 있게 상태만 표시하고 거르지 않았다.

**당시 확신도** — 순서는 높음(제휴 클릭 0회는 실측이다). 「수익화 필요」의 기준(제휴 링크 없음 + 조회 1회 이상)은 임의값이다 ⚠️

**재검토 조건** — 상위 10건을 채운 뒤 쿠팡·네이버 클릭이 실제로 발생하면 그때 상세 화면 분기로 넘어간다. 클릭이 여전히 0이면 화면이 아니라 다른 문제다.

## D-026 · 끝난 걸 아는데 마감일을 모를 때, 날짜 대신 "확인했다"를 남긴다 · 2026-08-23

**상태:** 유효 (`D-024`의 "「이미 끝났다」 버튼을 두지 않는다" 부분을 뒤집음)

**상황** — `D-024`에서 「이미 끝났다」 버튼을 **일부러 안 만들었다.** 실제 마감일을 모르는데 오늘 날짜를 `deadline`에 넣으면 화면에 우리가 모르는 마감일이 적히기 때문이었다. 그런데 바로 그 경우가 나왔다 — 사장님이 판매 페이지를 열어보고 "오르다 매쓰파워빌더스, 이건 판매 끝났잖어"를 확인했는데, 수집 12일째라 21일 규칙으로는 9일을 더 노출해야 했다.

**놓친 것** — `EndedDealNotice`는 `{post.deadline && ...}`로 **마감일이 있을 때만** 날짜를 쓴다. 즉 마감일이 비어 있어도 종료 안내가 정상으로 뜬다. 날짜를 지어낼 필요가 애초에 없었다. "언제 끝났나"가 아니라 "끝났다는 걸 확인했나"만 남기면 된다.

**결정** — `ended_at`(관리자가 종료를 확인한 시각)을 추가한다. `isExpired()`와 `isCustomerVisible()`이 이 값을 **가장 먼저** 본다 — 사람이 확인한 것이 날짜 계산보다 정확하다. 채우기 「미확인」·「마감일 미확인」 양쪽에 「이 공구 끝났어요」와 「종료 표시 취소」를 둔다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `deadline`에 오늘·어제 날짜를 넣음 | 우리가 모르는 마감일이 고객 화면에 적힌다. `D-024`에서 이미 버린 이유 그대로다 |
| `published = false`로 내림 | 목록에서는 빠지지만 `isExpired`가 false라 **상세는 "진행 중"으로 남는다.** 검색으로 들어온 사람이 살아 있는 공구로 본다 |
| `status = 'excluded'` | 상세가 404가 된다. `D-002`(마감 공구 URL을 살려둔다)를 정면으로 어긴다 |
| 21일이 지나기를 기다림 | 끝난 걸 아는데 9일을 더 노출한다. 그동안 검색 유입은 계속 들어온다 |
| `PeriodState`에 kind를 하나 더 추가 | `isExpired()` 한 줄이면 되는 일이다. 화면 분기가 늘고 `badgeFromState`·`periodTextFromState`를 또 손대야 한다 |
| 수집기가 자동으로 `ended_at`을 붙이게 | 자동으로 판단할 수단이 없다 — 인포크·블로그는 공구가 끝나도 페이지가 남고 네이버는 403이다(`D-024`). 자동 판단은 21일 규칙이 맡고, `ended_at`은 **사람만 쓴다** |

**받아들인 대가** — 필드가 하나 늘었다(선택 필드라 마이그레이션은 없다). 되돌리려면 사람이 「종료 표시 취소」를 눌러야 한다. 그리고 `ended_at`은 관리자 라벨에 `fmtDate`로 표시되는데, ISO 문자열의 UTC 날짜를 쓰므로 KST 새벽에는 하루 전으로 보인다 — `compare_none_at`도 같은 방식이라 일관되지만 정확하진 않다 ⚠️

**당시 확신도** — 높음. 종료 화면이 마감일 없이도 정상으로 뜨는 것을 코드와 실제 데이터로 확인했다.

**재검토 조건** — 「종료 표시 취소」를 자주 누르게 되면(잘못 눌렀다는 뜻) 확인 단계를 넣는다.

## D-025 · 관리자 경고를 "자동 수집이 멎었다"에서 "판정 없이 쌓였다"로 바꾼다 · 2026-08-23

**상태:** → `D-032`로 대체됨 (`D-020`을 뒤집었던 배너 자체가 우선순위 목록으로 바뀌었다)

**상황** — `D-020`으로 넣은 경고가 두 가지를 잘못 말하고 있었다.

첫째, 기준이 "비교가를 가진 공구 중 가장 최근 **수집일**"이었다. 그래서 오래전에 들어온 공구를 관리자가 손으로 채우면 시계가 앞으로 밀렸다. 자동 수집은 **2026-07-31에 끊겼는데** 경고는 "6일째"라고 말했다 — 8/17에 수집된 공구 한 건에 사람이 값을 넣어서다(`market_source`가 `naver_shopping`이 아니라 `null`이다). **일할수록 경고가 조용해지는 구조였다.**

둘째, "그 뒤로 들어온 129건에 비교가가 하나도 없다"고 했지만 그중 10건에는 `origPrice`·제휴 링크·옵션 비교가로 판정이 붙어 있었다. `market_price`만 봤기 때문이다.

그리고 더 근본적으로, **"자동 수집이 멎었다"는 이제 뉴스가 아니다.** 네이버가 API를 폐지했으므로(`D-019`) 이 값은 영원히 0이고, 매일 같은 말을 하는 경고는 결국 아무도 안 본다.

**결정** — 경고가 세는 것을 "자동 비교가 공백 일수"에서 **"고객에게 보이는데 판정이 없는 공구 수"** 로 바꾼다. 10건 이상일 때만 띄우고, 「채우러 가기」 버튼으로 채우기 화면으로 보낸다. 채우면 줄고, 다 채우면 사라진다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `market_source === 'naver_shopping'`만 세도록 고침 | 숫자는 정확해지지만 API가 폐지됐으므로 "23일째 → 24일째"로 **영원히 뜬다.** 끌 수 없는 경고는 없는 것과 같다 |
| 경고를 없앰 | 채우기 화면에 「미확인」 탭이 있지만 관리자 첫 화면에서 밀린 양이 안 보인다 |
| 수집분 전체를 셈 | 하루 46건씩 들어오는데 대부분 비공구로 제외되거나 검수 대기라 고객에게 안 나간다. "646건 중 608건"이라고 하면 겁만 주고 행동으로 이어지지 않는다 |
| 비율(%)로 표시 | 분모가 줄어도 비율이 오른다. 실제로 `D-024`로 마감일 미확인이 내려가면서 판정 대기가 34%→27%가 됐는데 좋아진 게 아니라 분모에서 끝난 공구가 빠진 것이었다 |
| `market_price`에 자동/수동 구분 필드 추가 | `market_source`가 이미 구분한다(`naver_shopping` vs `null`). 필드가 없어서가 아니라 **세는 대상이 잘못된 것**이었다 |

**받아들인 대가** — 자동 비교가 수단이 언젠가 생겨도(쿠팡 파트너스 등) 그게 멎는 걸 이 경고는 알려주지 않는다. 그때는 새 수단에 맞는 감시를 따로 붙여야 한다. 임계값 10건은 실측 근거가 없는 임의값이다.

**당시 확신도** — 높음. 옛 경고가 틀린 숫자를 말한다는 것을 운영 데이터로 확인했다. 임계값만 감이다 ⚠️

**재검토 조건** — 34건을 10건 밑으로 내린 뒤에도 자주 뜨면 임계값을 올린다. 자동 비교가 수단이 생기면 그 수단의 중단 감시를 별도로 만든다.

## D-024 · 마감일을 모르는 공구를 상시딜과 가르고 21일 뒤 내린다 · 2026-08-23

**상태:** 유효 (「이미 끝났다」를 두지 않기로 한 부분만 `D-026`으로 뒤집힘)

**상황** — 고객에게 보이는 110건 중 **44건이 마감일이 비어 있었고**, `getPeriodState()`가 그걸 전부 "상시딜"로 취급해 무기한 노출했다. 코드 주석에는 "마감일이 없다는 건 계속 판매된다는 뜻"이라고 근거가 적혀 있었지만, 실제로는 수집기가 **못 읽은** 경우가 대부분이었다 — 그중 33건이 수집한 지 15일이 넘었다.

검색 유입 상세 조회의 **48%(79명)** 가 이 44건에 몰려 있었고, **1위 착지 페이지(34명)는 40일 전 수집된 이미 끝난 공구**였다. 사장님이 직접 확인하다 발견했다("네이버쇼핑에서 최저가 찾기 → 이건 공구가 끝났네").

`check_links.py`가 매일 링크를 점검하지만 이건 구조적으로 못 잡는다. 8/21 실행에서 117건을 점검해 **0건**을 걸렀다.

**결정**

1. `PeriodState`에 `deadline_unknown`을 추가해 상시딜과 가른다. **관리자 플래그가 붙은 것만 상시딜이다.**
2. 시작일(없으면 수집일)로부터 `DEADLINE_UNKNOWN_DAYS = 21`일이 지나면 끝난 것으로 본다 — 고객 목록에서 내리고 상세는 종료 안내로 바꾼다. URL은 살려둔다(`D-002`).
3. 관리자에 **「마감일 미확인」 탭** — 조회 많은 순으로 보고 마감일을 넣거나 상시딜로 확정한다.
4. 고객 화면에는 "마감일 미확인"이라고 쓰지 않는다. 배지를 안 붙이고 "OO부터 진행 중"까지만 말한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 지금처럼 마감일 없으면 상시딜 | 이미 끝난 공구가 최상위 착지 페이지로 남는다. 판정이 없는 것보다 나쁘다 — "모른다"고 말하는 게 아니라 **틀린 말**을 하는 것이라 판단 기준 1번에 걸린다 |
| `check_links.py`를 고쳐서 감지 | **구조적으로 안 된다.** 인포크 링크페이지(9건)와 네이버 블로그(3건)는 공구가 끝나도 페이지가 그대로 남고, 네이버 계열 21건은 403이라 아예 못 읽는다 |
| 수집기가 "못 찾음"을 새 필드로 기록 | 기존 2,350건에 소급이 안 된다. 관리자 플래그 유무로 이미 구분된다(51건이 상시딜로 표시돼 있다) — 필드를 늘리지 않고 파생으로 얻는다 |
| N = 14일 | 목록이 110→77로 준다. 마감일을 못 읽었을 뿐 진행 중인 공구까지 내려갈 위험이 커진다 |
| N = 30일 | 40일째 공구가 9일을 더 버틴다. 공구가 대개 2~3일이면 끝나는 걸 감안하면 너무 길다 |
| 자동으로 안 내리고 관리자 확인만 | 44건이 쌓여 있고 계속 는다. 사람이 볼 때까지 틀린 말이 계속 나간다 |
| 고객에게 "마감일 미확인"이라 표시 | 우리 사정이다(원칙 3). 고객이 그 말을 듣고 할 수 있는 일이 없다 |
| 「이미 끝났다」 버튼으로 오늘 날짜 넣기 | 실제 마감일이 아닌 날짜가 화면에 적힌다. 모르면 그냥 두고 자동으로 내려가게 하는 편이 정확하다 |

**받아들인 대가**

- 고객 목록이 **110 → 88건(20% 감소)**. 내려간 25건이 최근 14일 41명의 조회를 받고 있었다.
- 진짜 상시딜인데 관리자가 플래그를 안 단 공구도 21일 뒤 내려간다. 「마감일 미확인」 탭에서 되살릴 수 있지만 사람이 봐야 한다.
- `DEADLINE_UNKNOWN_DAYS`가 `lib/period.ts`와 `check_links.py` **두 곳**에 있다. 기술부채 #5와 같은 모양이라, 주석으로 서로를 가리키게 하고 운영 데이터 2,350건 전체에 대해 두 구현의 결과가 일치하는지 대조했다(불일치 0).
- `isEvergreen()`의 뜻이 좁아져서 홈 "상시딜" 탭에 뜨던 공구가 준다. 사람이 확인한 것만 남으므로 정확해지는 방향이지만 눈에 띄는 변화다.

**당시 확신도** — 상시딜과 가르는 것은 높음. **21일은 사장님이 정한 값**이고 실측으로 검증된 기준은 아니다 ⚠️

**재검토 조건** — 「마감일 미확인」 탭에서 "상시딜이 맞다"로 되살리는 일이 잦으면 기간을 늘린다. 반대로 21일 안쪽인데 이미 끝난 공구가 계속 발견되면 줄인다.

## D-023 · 비교가 작업 상태를 셋으로 가르고, 후보 탐색을 provider로 뺀다 · 2026-08-22

**상태:** 유효

**상황** — 비교가가 없는 공구가 한 덩어리였다. 아직 아무도 안 본 것과, 사람이 다 찾아본 끝에 비교할 게 없다고 확인한 것이 같은 목록에 섞였다. 그래서 목록이 줄지 않고 같은 공구를 몇 번씩 다시 뒤지게 되며, 남은 일이 몇 건인지도 알 수 없었다. 게다가 자동 비교가 수단이 전부 막힌 상태(`D-019`)라 사람이 채워야 하는데 매번 맨손 검색이었다.

**결정**

1. 비교 상태를 **미확인 / 비교가 있음 / 비교불가** 셋으로 가른다(`lib/compareState.ts`).
2. **비교불가는 사람이 확인하고 명시적으로 고른 상태만이다.** 자동으로 되는 경로는 없다.
3. 셋 중 저장하는 건 비교불가뿐이다(`compare_none_at` / `_reason` / `_note`). 나머지 둘은 값에서 파생한다.
4. 채우기 화면이 **동일상품 후보를 먼저 내밀고**, 관리자가 고르면 그 가격이 비교가로 저장된다.
5. 후보 탐색은 provider 목록(`lib/compareCandidates.ts`)으로 분리한다. 지금은 우리 안에 있는 값만 쓰고, 외부 수단은 나중에 provider 하나를 더 넣는 것으로 붙인다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| `VerdictState`에 상태를 추가 | 검수 상태가 고객 화면으로 새어 나간다(원칙 3). 핵심 enum이 커지고 카드·상세·공유카드·정렬을 다 손대야 하며 `D-005`·`D-018`을 흔든다 |
| 세 상태를 모두 필드로 저장 | 비교가 있음·미확인은 값에서 바로 나온다. 저장하면 값과 상태가 어긋날 수 있고, 2,317건 일괄 마이그레이션이 필요한데 `savePosts()`에 락이 없다 |
| 비교불가를 자동으로 판정 | "아직 안 봤다"와 "보고 없었다"가 다시 섞인다. 자동으로 붙으면 사람이 확인할 이유가 사라져서 나눈 의미가 없어진다 |
| `is_exclusive_deal`로 비교불가를 대신 | 단독 판매는 비교불가의 네 가지 이유 중 하나일 뿐이다. 게다가 그 필드는 고객 화면 문구를 바꾸는데, 이번 결정은 고객 화면을 건드리지 않기로 했다 |
| 사유를 자유 입력으로 | 나중에 세어 봐야 다음에 뭘 자동화할지 안다. 자유 문구는 집계가 안 되고 매번 문장을 지어내야 해서 손도 더 간다 |
| 후보 탐색용 새 API 라우트 | 관리자 화면이 이미 전체 목록을 들고 있다. 새 라우트는 `middleware.ts` 양쪽 등록이 필요하고 보호 표면만 늘어난다 |
| 후보를 자동으로 비교가에 적용 | 잘못 고른 후보가 그대로 틀린 비교가가 된다. 판단 기준 1번을 정면으로 어긴다 |
| 브랜드가 같으면 후보로 인정 | **실측으로 배제했다** — 같은 브랜드의 "밥 도자기"와 "소창행주"가 서로 후보가 됐다. 브랜드를 낱말 비교에서 빼고, 상품명이 최소 하나는 겹치게 조였다 |
| `market_price`를 값과 무관하게 후보로 | 27,500원짜리 감자빵에 70원이 후보로 뜬다. 공구가의 20% 미만은 후보가 아니라 모든 행에 붙어 다니는 소음이다 |

**받아들인 대가**

- 후보가 잡히는 건 미확인 46건 중 **8건(17%)** 뿐이다. 나머지는 여전히 맨손 검색이다. 조이기 전에는 19건이 잡혔지만 "밥 도자기 ↔ 소창행주" 같은 게 섞여 있어서, 넓은 후보보다 믿을 수 있는 후보를 골랐다.
- 후보를 클라이언트에서 계산한다. 외부를 부르는 provider가 붙는 시점에는 서버 경로가 필요해지고, 그때 라우트를 만들어야 한다.
- 고객 화면은 그대로라 판정 대기 비율은 이 작업만으로는 안 줄어든다. 줄어드는 건 관리자가 같은 공구를 다시 뒤지는 일이다.

**당시 확신도** — 상태 3분류는 높음. 후보 매칭 문턱(`hits >= 2`, 브랜드가 같으면 `score >= 0.34`)과 소음 하한(20%)은 실측 46건에 맞춘 값이지 검증된 기준이 아니다 ⚠️

**재검토 조건** — 후보 적중률이 낮아 아무도 안 쓰면 문턱을 풀거나 provider를 늘린다. 비교불가가 쌓이면 사유 분포를 세어 다음 자동화 대상을 정한다 — `not_found`가 많으면 검색 수단이, `no_same_set`이 많으면 세트 단위 비교가 부족한 것이다.

## D-022 · 문서의 숫자를 사람이 아니라 스크립트가 다시 잰다 · 2026-08-21

**상태:** 유효

**상황** — `03-SYSTEM.md`의 숫자 20여 개가 지금도 맞는지 확인할 방법이 사람의 기억뿐이었다. 실제로 재보니 판정 대기가 문서에는 26%로 적혀 있었지만 실측 34%였다(8월 수집분만 보면 47건 중 22건, 47%). 아무도 코드를 안 고쳤는데 문서가 낡은 것이라, 네이버 API 폐지를 3주 동안 몰랐던 것(`D-020`)과 같은 모양의 고장이다.

**결정** — `scripts/check-docs.js`가 `03-SYSTEM.md`의 숫자를 다시 재서 **어긋난 것만** 알린다. 기대값은 스크립트가 아니라 문서에서 정규식으로 뽑고, 판정·공개 여부 규칙은 `lib/`의 TS를 그대로 불러 쓴다. 값은 세 종류로 나눈다 — `fixed`(정확히 일치), `moving`(20% 넘게 벌어질 때만), `server`(운영 서버에서만 유효).

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 기대값을 스크립트에 숫자로 박아두기 | 고칠 곳이 두 곳이 된다. 기술부채 #5(구매 링크 규칙이 TS·파이썬 양쪽에)와 똑같은 문제를 하나 더 만드는 일이다 |
| 판정·공개 규칙을 JS로 다시 구현 | 같은 이유. `typescript`가 이미 devDependency에 있어 require 훅으로 `getDealVerdict()`·`isCustomerVisible()`·`app/sitemap.ts`를 그대로 호출할 수 있었다 |
| `tsx`·`ts-node` 같은 실행기 추가 | `typescript.transpileModule`로 충분했다. 의존성을 늘릴 이유가 없다 |
| 전 항목 정확히 일치 요구 | sitemap URL 수처럼 수집이 돌면 당연히 움직이는 값이 매번 실패로 뜬다. 그러면 결국 아무도 안 보게 되고, 막으려던 고장을 그대로 다시 만든다 |
| 스크립트가 문서를 자동으로 고치게 | 숫자가 왜 움직였는지는 사람이 봐야 한다. 판정 대기 26%→34%는 조용히 고쳐 쓸 게 아니라 알아야 할 사실이었다 |
| CI에 붙이기 | CI가 없다. 배포 전 체크리스트에 넣었다 |

**받아들인 대가** — 정규식이 문서의 표현에 묶인다. 실제로 "공개 86건 중 pending"을 "보이는 공구 112건 중 pending"으로 고치면서 정규식도 같이 고쳐야 했다. 대신 표현이 바뀌면 `⚠️ 문서에서 못 찾음`이 떠서 조용히 깨지지는 않는다.

그리고 **숫자만 지킨다.** 서술형 주장("손대면 위험한 곳", 기능 목록)과 운영 서버에만 있는 값(이미지 용량 78MB·431MB, 백업, cron, 환경변수)은 검증 대상이 아니다.

**당시 확신도** — 높음. 21항목이 실제로 돌았고 어긋난 3개를 잡아냈다. 다만 `moving` 허용치 20%는 실측이 아니라 임의로 정한 값이다 ⚠️

**재검토 조건** — 오탐이 잦아 무시하게 되면 허용치를 올린다. 서술형 주장까지 지키고 싶어지면 그건 다른 도구가 필요하다.

**재검토 조건** — 한쪽 등록을 정리하기로 하면 그때 해당 코드를 뺀다.

## D-019 · 네이버 쇼핑 비교가를 포기하고 대체 수단을 찾는다 · 2026-08-20

**상태:** 진행 중 ⚠️ (대체 수단 미확정)

**상황** — 네이버 쇼핑 검색 API가 `404 SE05 (존재하지 않는 검색 api)`를 반환한다. 같은 키로 블로그·뉴스·백과는 200을 주고 쇼핑·책만 404다. 앱 권한 문제가 아니라 **네이버가 그 API를 폐지한 것**이라 설정으로 되살릴 수 없다. 이 API가 판정의 주 재료였다(`market_price` 711건).

**결정** — 네이버 쇼핑 API 복구를 기대하지 않는다. 쿠팡 파트너스 Open API를 1순위 대체 수단으로 검토한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 네이버 개발자센터에서 권한 재설정 | 실측으로 배제했다 — 앱의 `검색` 권한은 살아 있고 다른 검색 API는 정상 응답한다. 우리가 손댈 수 있는 게 없다 |
| 네이버 쇼핑 웹페이지 스크래핑 | 브라우저 헤더를 다 갖춰도 429로 하드 차단한다 (실측) |
| 다나와·에누리 등 가격비교 사이트 | 공개 API가 없어 결국 스크래핑이고, 같은 차단 문제로 돌아온다 ⚠️ 실제 확인은 안 했다 |
| 상세페이지 정가(`origPrice`)만으로 판정 | 판매자가 스스로 적은 정가라 부풀릴 수 있다. "시중 가격 대비"보다 근거가 약하다 |
| 관리자 수동 입력만 | 밀린 656건을 사람이 다 볼 수 없다 |

**쿠팡 파트너스를 1순위로 본 이유**
- 계약 기반이라 정책 한 번에 사라질 위험이 낮다 (네이버 무료 공개 API가 그렇게 사라졌다)
- 한 번의 호출로 **비교가와 구매 링크를 함께** 준다 — `market_price`와 `purchase_links`(현재 6건뿐)를 동시에 채운다
- 고객이 링크를 눌러 즉시 확인할 수 있는 근거가 된다
- 판정 로직이 `purchase_links` 가격을 이미 `verified`(사람 확인급)로 취급한다 — 코드 변경이 적다

**받아들인 대가** — 비교 기준이 "시중 최저가"에서 "쿠팡 가격"으로 바뀐다. 쿠팡에 없는 상품(자사몰·소규모 브랜드)은 여전히 판정 불가다. 커버리지는 ⚠️ 미측정 — API 키를 받는 대로 판정 대기 30건으로 먼저 재기로 했다.

**당시 확신도** — 낮음. 쿠팡 파트너스 Open API의 승인 조건과 실제 커버리지를 확인하지 못했다.

**재검토 조건** — 커버리지 측정 결과가 절반에 못 미치면 정가 기반 판정으로 방향을 다시 잡는다.

## D-018 · 판정 대기 배지를 목록에서 빼고 상세에서만 설명한다 · 2026-08-20

**상태:** 유효

**상황** — 고객에게 보이는 공구 86건 중 22건(26%)이 "판정 대기" 배지를 달고 있었다. 4장 중 1장 꼴이다.

**결정** — 목록 카드(`PostCard`, `DealStrip`)에서는 pending일 때 배지를 그리지 않는다. 상세에서만 "가격 비교 전 — 아직 다른 곳에서 같은 상품을 찾지 못했어요"로 설명한다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 그대로 두기 | 다른 배지는 읽는 즉시 쓸모가 있는데("사도 된다", "다른 데 봐라") 판정 대기만 우리 사정을 적은 말이라 읽어도 판단이 안 선다. "대기"는 곧 나온다는 약속처럼 읽혀서 다시 와도 그대로면 신뢰가 깎인다 |
| 문구만 `비교가 없음`으로 변경 | 여전히 우리 사정 얘기다. 고객에게 무의미한 건 같다 |
| 문구를 `단독 상품일 수 있어요`로 변경 | **사실이 아닐 수 있다.** 관리자가 직접 확인한 `is_exclusive_deal`(단독 공구)과 섞이면 확인한 것과 모르는 것이 구분되지 않는다 |

**받아들인 대가** — 목록에서 "판정이 있는 것"과 "없는 것"이 구분되지 않는다. 사용자는 상세에 들어가야 안다.

**당시 확신도** — 보통. 배지가 빠져 꿀딜이 더 도드라지는 부수 효과는 확인했지만, 이탈률 변화는 측정하지 못했다.

**상태:** 유효

**상황** — "공구 글 1개 = 상품 1개"로 보면 세트가 7~8개인 공구를 담을 수 없다. 게시물에 판매가 하나·비교가 하나만 두면 어느 세트 기준인지 알 수 없고 판정도 그 하나로만 나온다.

**결정** — `Post.options: DealOption[]`을 두고, 비교가를 게시물이 아니라 **세트마다** 갖게 한다. 옵션에 비교가가 하나라도 있으면 판정이 옵션 경로를 탄다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 게시물을 세트 수만큼 쪼개기 | 같은 공구가 목록에 7번 나온다. 마감일·인플루언서가 중복된다 |
| 대표 세트 하나만 저장 | 어느 구성 기준인지 알 수 없고, "골라담기"류는 표현 자체가 안 된다 |
| 옵션 유무와 무관하게 옵션 경로 우선 | **실제로 그렇게 만들었다가 되돌렸다.** 자동 수집 옵션은 비교가가 없어서, 옵션이 붙는 순간 잘 나오던 판정이 "판정 대기"로 후퇴하고 등급 근거였던 비교표까지 화면에서 사라졌다 |

**받아들인 대가** — 옵션이 있는 공구와 없는 공구의 판정 경로가 둘로 갈린다(`verdictFromOptions` vs 단일 경로). 화면도 두 벌이다.

**당시 확신도** — 높음.

**재검토 조건** — 없음.

## D-007 · 관리자 방문 제외를 세 겹으로 한다 · 2026-08-16

**당시 확신도** — 높음.

**재검토 조건** — 실사용자가 늘어 IP 제외로 잃는 방문이 유의미해질 때.

## D-006 · 자동 매칭 가격에 신뢰 하한을 둔다 · 2026-08-18

**상태:** 유효

**상황** — 데코아르 드라이기(공구가 59,000원)가 아쉽딜로 판정됐다. 자동 매칭된 네이버 가격이 19,800원으로 잘못 잡혀 있었고, 기준가를 후보 중 최솟값으로 고르는 로직이 그걸 채택했다. 같은 문제가 **26건** 있었다(신일 제습기 399,000원 → 2,900원 등).

**결정** — 사람이 확인한 값(`verified`)과 자동으로 긁은 값(`auto`)을 나눠 담고, 자동값이 공구가의 50%(`AUTO_MATCH_FLOOR`) 미만이면 기준에서도 화면에서도 뺀다.

**검토한 대안과 버린 이유**

| 대안 | 버린 이유 |
|---|---|
| 최솟값 그대로 사용 | 잘못된 매칭 하나가 판정을 뒤집는다. 이게 원래 버그였다 |
| 자동 매칭 전면 폐기 | `market_price`가 711건으로 판정의 주 재료다. 버리면 대부분이 판정 대기가 된다 |
| 관리자가 전부 수동 검증 | 2,300건을 사람이 다 볼 수 없다 |

**받아들인 대가** — 진짜로 절반 이하로 싼 상품(정당한 초특가)도 걸러진다. 그런 경우 관리자가 `market_price`를 직접 고쳐 넣어야 한다.

**당시 확신도** — 높음. 적용 후 분포가 아쉽딜 31→5, 꿀딜 23→41로 바뀌었다.

**재검토 조건** — 하한 50%가 정당한 딜을 자주 거른다는 사례가 쌓이면 조정한다.

## D-004 · 판정 등급을 4단계로 하고 임계값을 고정한다 · 2026-08-17

**재검토 조건** — 카테고리별로 할인율 분포가 크게 다르다는 게 데이터로 확인되면.
